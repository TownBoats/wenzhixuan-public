# Agent 升级开发过程复盘

基准：2026-11-01，源码 `347a6a4`。本文提取本次 A–G 迁移和后续探索中的工作方式；不声称已测量开发提效百分比或达到企业合规标准。原件均在 [阶段归档](../archive/agent-upgrade-2026-11-01/README.md)，历史相互矛盾时保留原文并单列解释。

## 1. 本次实际建立了什么

这次的轻量 Harness 包含六条相互连接的控制线：

| 环节 | 原始载体 | 起到的作用 |
| --- | --- | --- |
| 约束与边界 | 两份 `RULE.mdc`、核心协议、禁用清单 | 限制越层、旧路径改写、协议污染和不实完成声明 |
| 任务与依赖 | 总纲、A–F 工作包、阶段开发指导 | 将迁移拆成带输入、判据、证据的可核对任务 |
| 人工决策 | 决策台账、开工前选项讨论 | 明确产品语义、兼容策略和范围，而非由 Agent 猜测 |
| 分层验证 | 端点探针、SDK mock、reducer/hook 测试、浏览器走查 | 针对外部协议、并发、状态和体验建立不同证据 |
| 验收与阶段关闭 | F 验收记录、用户逐项确认、阶段收尾 | 将 Agent 自检和用户接受分开 |
| 跨会话交接 | HANDOFF、会话日志、证据位置 | 保存接续位置、失败与未完成工作 |

其价值在于形成了可追溯链，而不是规则文字本身：一个功能可以追到需求、决定、实现、证据和人工接受。

## 2. 阶段组织的理由

| 阶段 | 首要风险 | 交付与进入下一步的依据 |
| --- | --- | --- |
| A 基线与端点 | SDK 与真实服务不一致、旧实现不可回退 | 依赖/基线档案、真实工具闭环探针、端点限制记录 |
| B 运行层 | 传输、工具、副模型、副作用混在页面 | 无 React 的运行入口、工具执行/降级、预算与取消、mock 和真实单跑 |
| C 会话层 | 乱序、迟到、双击、上下文与展示相互污染 | 纯 reducer、命令式 hook、上下文/展示投影、Node 闭环 |
| D 页面接入 | 纯函数通过但浏览器无法实际作答 | 工具卡、问题组、配置门槛、提示词迁移、真实交互走查 |
| E 历史恢复 | 旧数据损坏、刷新重放、假保存成功 | v2 存储、v1 只读投影、恢复与错误提示、历史抽屉 |
| F 故障与集成 | 正常流程掩盖取消/重试/错误缺陷 | 取消、最后轮重试、错误分类、逐项集成验收 |
| G 配置与体验 | 新路径缺配置入口、阅读/作答体验粗糙 | 三段设置面板、保存即生效、开关退役、Markdown/磁贴与版式 |
| 后续探索 | 生成内容、流式协议与新端点兼容 | HTML/SVG 卡、参数预览、结构化副模型、触屏与等待设置 |

这种依赖顺序让外部高风险先被验证，也让状态机可在 UI 之前独立检查。后续探索没有独立的 A–G 编号，不能仅靠旧阶段表推断全部新增功能的验收状态。

## 3. 有效机制及真实案例

### 3.1 先做外部风险探针

A3/A4 用真实端点输出判断支持边界，记录 `parallelToolCalls:false` 被接受但未限制并发，以及 reasoning 的实际返回方式。结论进入 A-5/A-6，应用层仍需去重和并发控制。它避免把 API 参数被接受误认为语义已执行。

证据：[A 基线](../archive/agent-upgrade-2026-11-01/agent-mvp/A-基线存档.md)、[决策 A-5/A-6](../archive/agent-upgrade-2026-11-01/agent-mvp/决策记录.md)。原始输出文件被忽略，本轮本地归档中只有原文摘要与索引，不能声称所有原始请求响应已可重放。

### 3.2 契约和行为测试揭示并发问题

C4 的会话闭环按 1/3/2 顺序返回问题结果，暴露了“按完成顺序排列问题”的缺陷；修复后按调用顺序展示。C3 的旧 runId、取消后迟到和双击用例，把“状态不变”的约束落为可重复检查。

证据：[HANDOFF 的 C3/C4 日志](../archive/agent-upgrade-2026-11-01/agent-mvp/HANDOFF.md)、[conversationState.test.js](../../src/utils/__tests__/conversationState.test.js)、[session-loop.mjs](../../scripts/session-loop.mjs)。

### 3.3 重试验收检查真实的跨运行身份

F2 发现 SDK 的 `partId` 可在不同运行重复为 `0`，只用 `partId` 合并会把新旧正文拼在一起；只改合并逻辑后又暴露 React key 重复。最终合并键和渲染 key 都含 `runId`。这说明验收应检查用户观察到的行为，不能仅以“重试按钮触发了请求”作为判据。

证据：[决策 F-3](../archive/agent-upgrade-2026-11-01/agent-mvp/决策记录.md)、[会话投影](../../src/utils/conversationState.js)、[MessageContent](../../src/components/MessageContent/MessageContent.jsx)。

### 3.4 浏览器失败路径补足纯逻辑测试

D8 真端点走查发现工具卡降级态不可达、问题卡状态不符、没有候选答案时无法手动回答、窄屏按钮折行。D-5/D-6 的修复与后续复测完成了“服务失败仍可学”的完整链路。纯函数返回 `optionsStatus:'unavailable'` 不能证明学生真的看得到可输入的表单。

证据：[D8 日志](../archive/agent-upgrade-2026-11-01/agent-mvp/HANDOFF.md)、[决策 D-5/D-6](../archive/agent-upgrade-2026-11-01/agent-mvp/决策记录.md)、[F 验收](../archive/agent-upgrade-2026-11-01/agent-mvp/F-验收记录.md)。

### 3.5 决策记录保留“为什么没有选另一条路”

多题、作答自动续轮、v2 新键、运行中禁止切会话、保留重试旧内容等都有明确产品语义。它们不仅影响函数实现，也影响学生体验和恢复策略。决策台账使后续能识别“有意保留的风险”和真正回归。

例如 F-3 保留重试后的旧 pending 问题，并注明风险；后续评审不能未经讨论就把这一语义当成无条件应修的缺陷。

## 4. 重要决策如何演进

| 主题 | 演进 | 需要保留的认识 |
| --- | --- | --- |
| 提问数量 | B-3 确认一轮多个问题，每个调用保留配对结果 | “软引导 2–3 问”与“代码硬限制数量”不同 |
| 副模型边界 | 初始复用旧 AgentModel 倾向 → B-10 独立适配 → `afa3040/f1259c2` 结构化工具通道 | 设计先后有版本，不把旧理由当成现行实现 |
| 教学模式 | normal 无工具、socratic 有工具；D2 控件按 B-1 裁剪 | 代码存在模式不等于用户有切换入口 |
| 不支持工具时的策略 | B-6 收窄兜底触发条件 → D-2/D-3 明确不自动降级、显示原因并建议换端点 | 缺副模型仍可手答，不应混同主端点不支持工具；建议动作必须在界面可执行 |
| 存储 | E-1 等明确新键写入、旧键适配读取 | 源码旧路径退役不代表旧用户历史退役 |
| 发布开关 | F-6 默认新路径 → G-1 移除开关 | 回退从页面开关变成版本回退，文档应随之更新 |
| 展示协议 | G 界面改版 → HTML/SVG 工具 → `b8d5852` 参数流式预览 | 每个新工具与事件都应触发现行协议和验收范围更新 |

这些变化本身是正常学习；问题在于变更没有始终同步到现行知识，导致 B-10、旧规则、源码之间出现多个“当前真相”。

## 5. 流程失效与修正

| 失效现象 | 真实表现 | 本轮提取的修正 |
| --- | --- | --- |
| 交接膨胀 | 约 1,500 行，旧下一步与最新完成状态并存 | 当前快照覆盖更新，历史冻结；稳定知识移出交接 |
| 规则寿命无限 | G 已结束，规则仍要求 A→F 串行和旧文件永久禁改 | 长期不变量与阶段约束分离，阶段关闭时退役后者 |
| 规则重复 | `.agent` 和 `.codebuddy` 各维护 247 行相同正文 | 根共享规则作为正文，工具配置仅保留短入口 |
| 证据外推 | 10-18 测试计数沿用到新增工具后的 HEAD，旧 dist 走查被混同源码验证 | 证据绑定代码/制品基准，分开注明历史引用与当前执行 |
| 状态压成单一“完成” | 人工验收与自动验证受阻被反复捆绑 | 实现、验证、验收、发布独立记录 |
| 诊断从推测升级为结论 | 会话侧 junction 失败被说成机器/代码/锁文件健康的确定判断 | 保留观察、假设、反证、待验证项；不据不明根因反复重装 |
| 文档误导删除 | 把 MarkdownRenderer 称为死代码，忽略新 AnswerCard 的引用 | 代码引用图优先，删除前核查共享依赖与数据兼容 |
| 计数口径混淆 | 把 118 当完整用例数，把新增行比例称业务重写比例 | 测试区分文件级失败；统计注明范围、类型和净值 |
| 一次性冒烟与长期回归混用 | B1 冒烟脚本删除后，B6 交付前没有自动红灯；多处浏览器证据也不可 CI 复跑 | 交付时标清一次性/可复跑；关键判据及时进入自动测试，现场证据保留环境、日期和原始结果 |
| 资料没有进入版本控制 | 大部分规则和 docs 被忽略 | 明确本地归档与已提交/远端归档的不同状态 |
| 门槛过细的风险 | 原流程每任务重读多份文档、逐项等待，存在形成仪式成本的可能；本次未测量效率损失 | 按风险设置任务契约和人工决策点，授权内持续推进；这是复盘建议，不是已测得提效 |

## 6. 不能从本次推得的结论

不能从历史 mock 推得所有服务都支持工具，不能从 sandbox 属性推得生成内容已全面安全，不能从纯前端推得凭据绝不会泄露，不能从 G 人工验收推得当前所有自动检查已通过，也不能用一份哈希清单声称具备企业审计能力。

本项目没有在本轮建立 CI 必检、PR 保护、制品签名、部署审计、数据迁移演练或完整安全回归。这些应作为企业级扩展任务单独设计。

## 7. 下一轮可测量的改进

建议观察：接手时必读资料量、从问题到证据的追溯成本、重开已定决策的次数、协议改动后的文档同步情况、因环境/测试/代码分别引起的失败、未关闭风险的持续时间。

本次未建立历史工时和对照组，不能给出提效百分比。下一阶段如要评估 Harness，应先定义上述口径，再保存样本；不要把更多规则、更多测试行数或更少人工交流本身当成目标。
