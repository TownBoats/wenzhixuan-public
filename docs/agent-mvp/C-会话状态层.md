# 阶段 C · 会话状态层

估时 2.5 小时｜任务 C1–C4｜依赖 B 通过｜产出：纯函数状态归并 + `useChatSession`，在 Node 里跑通"发送 → 待答 → 作答 → 新一轮"

## 1. 要解决什么

把"谁在什么时候改状态"从页面收回到一个地方。现状有五个具体病灶：

| 病灶 | 位置 | 后果 |
| --- | --- | --- |
| 两套消息数组各自可写 | `ChatPage` 的 `messages` + `uiMessages` | 已经分叉：作答摘要进了 `messages` 却没进 `uiMessages` |
| 加载状态有两个写入者 | `runAssistantTurn` 与 `useAgentsConfig` 的 `onRequestStart/End` 回调 | 副模型也可能触发状态变化，布尔值无法表达"谁在忙" |
| 没有取消能力 | `AgentModel` 内部创建超时控制器 | 用户离开或切换会话时，旧请求仍在写界面 |
| 迟到数据无身份 | 回调只带文本 | 无法判断片段属于哪一次运行，只能照着往里写 |
| 作答后靠 effect 隐式发下一轮 | `ChatPage:354-386` | "所有问题都回答完"这个观察条件与真实语义（谁在什么时候开始下一轮）耦合，重复渲染可能触发两次 |

## 2. 为什么这样做

### 2.1 为什么新建会话层，而不是先重构旧 `ChatPage`

| | 新建（推荐） | 先重构旧页面 |
| --- | --- | --- |
| 工作量 | 会话层只写一遍 | 同一段逻辑搬进 hook 一次，再替换成新协议一次 |
| 18 日投递 | 旧页面原样可用，随时可回退 | 重构期间旧页面处于不可用或半可用状态，风险落在要投递的版本上 |
| 代码重复 | 短期两套并存 | 无重复，但重复的是一次性成本 |

**倾向新建**。核心考虑不是工作量，而是**风险归属**：旧路径是投递的保底版本，任何改动都可能让它出问题；新路径即使失败也不影响投递。用开关切换（D1）把两者隔开，回退成本是零。

代价要认：验收通过后需要额外一步下线旧路径（已记入总纲第 7 节）。

### 2.2 为什么用 `runId` 而不是 `isLoading` 判断迟到数据

`isLoading` 回答的是"现在有没有东西在跑"，`runId` 回答的是"这条数据属于哪一次运行"。需要判断的是后者：

- 用户点了取消 → 运行 X 还在吐字 → 此时又发起了运行 Y → 没有 `runId` 时，X 的片段无法与 Y 区分；
- 切换会话 → 旧会话的运行没停 → 片段会写进新会话；
- 重试 → 同一条用户消息对应两次运行。

身份比状态可靠。所以规范事件里每个事件都带 `runId`（`01-核心协议.md` 第 4 节），会话层只接受当前运行的事件。这个判断是纯函数，可以测。

### 2.3 为什么用 `useReducer` 而不是多个 `useState`

会话状态是有序的、相互依赖的：一次工具完成会同时改变工具卡、问题状态和运行状态。多个 `useState` 会产生多次渲染和中间态（例如"问题已存在但状态还是 streaming"）。reducer 让一次事件变成一个原子转换，并且 `conversationState.js` 里的归并函数可以在 Node 里直接测，不需要渲染组件。

**不引入状态库**（Redux/Zustand）：本期只有一个会话在跑，reducer 足够；引入库会带来"为什么用这个库"的额外决策成本，而两天窗口里决策成本比代码成本更贵。

### 2.4 为什么作答要在同一个状态转换里完成三件事

"记录答案 → 关闭待答状态 → 开始新运行"必须是一次原子转换。现在的实现把它们拆在 effect 里（观察条件满足才触发），带来两个问题：界面会短暂显示"还没有回答"和"已经在生成"的混合态；重复渲染可能触发两次。放进 reducer 后，双击只会产生一次转换——因为转换的条件是"该问题仍是待答状态"，第一次转换后条件不再成立。

### 2.5 为什么上下文只取已配对的协议消息

下一轮请求要带上模型自己的调用记录，否则它会重复提问或否认问过。但不完整的调用（只有 call 没有 result）会让上下文非法，部分端点直接报错。所以 `buildModelContext` 只纳入配对的、已完成的 turn；未配对的留作展示和诊断，不发送。

## 3. 需要你决策的点

### 决策 1：作答后是否自动开始下一轮

| 选项 | 说明 | 代价 |
| --- | --- | --- |
| A. 作答即自动开始下一轮（保持现有产品行为） | 学生选完档位，界面立刻继续教学 | 学生没有机会补充"其实我不太确定" |
| B. 作答后需再点一次发送 | 多一步操作 | 与现在的体验不同，演示时多一次点击 |

**倾向 A**，因为本次改造明确"不改变手动选择模式的交互风格"，保持既有体验能减少变量。但要把实现方式从"effect 观察"改成"命令内转换"（见 2.4）。

### 决策 2：跳过问题的语义

方案里提到"提供明确的跳过问题操作"，但没定义跳过之后发生什么。

| 选项 | 说明 |
| --- | --- |
| A. 把跳过记录成一次真实回答（例如"我暂时不想回答这个问题"），进入下一轮（倾向） | 教学能继续，且模型知道学生回避了这个问题 |
| B. 仅关闭卡片，不下发任何内容 | 界面回到可输入状态，但模型不知道为什么卡住了 |

**倾向 A**。理由：卡片的关闭是界面行为，与"学生说了什么"是两件事；把跳过伪装成"关闭"会让下一轮上下文缺少信息，模型可能又提同一个问题。

跳过按钮本身是**可裁剪项**（总纲 5.7），时间不够时先不做，但语义要在这里定下来，避免 D 阶段临时发明。

### 决策 3：失败重试的用户入口

方案定的是"只允许重试最后一轮"。需要确认：

- 重试入口放在哪里？（现有实现是消息气泡上的重试按钮，主气泡和用户气泡各有一个。）
- 重试期间界面显示什么？（倾向：保留原有内容并显示"重新生成中"，不要清空——清空会让用户以为内容丢了。）

## 4. 任务清单

### C1 · `src/utils/conversationState.js`（纯函数）

**做法**：导出四个函数，全部无副作用。

| 函数 | 作用 |
| --- | --- |
| `reduceSession(state, action)` | 所有状态转换的入口：`SEND_MESSAGE`、`RUN_STARTED`、`TEXT_DELTA`、`REASONING_DELTA`、`TOOL_STARTED`、`TOOL_COMPLETED`、`TOOL_FAILED`、`RUN_FINISHED`、`SUBMIT_ANSWER`、`SKIP_QUESTION`、`CANCEL_RUN`、`RETRY_LAST_TURN`、`OPEN_CONVERSATION`、`SET_MODE` |
| `buildModelContext(turns)` | 组装下一轮的模型上下文 |
| `projectTurns(turns)` | 生成渲染数据（正文片段、工具卡、问题卡） |
| `deriveViewState(state)` | 派生 `isRunning`、`pendingQuestion`、`canChangeMode` 等，避免散落的布尔量 |

要点与理由：

- **`runId` 守卫**：所有运行事件先检查 `action.runId === state.turns.at(-1)?.runId`（或当前运行指针），不匹配直接返回原状态。**为什么返回原状态而不是报错**：迟到事件是正常现象（取消、切换会话都会产生），报错会污染日志和界面。
- **`toolCallId` 幂等**：`TOOL_STARTED` 遇到已存在的 `toolCallId` 视为更新，不追加新卡；`TOOL_COMPLETED` 找不到对应卡片时应先补建再更新（说明 SDK 的顺序与我们的假设不同），不要静默丢弃。
- **`SUBMIT_ANSWER` 的原子性**：一次 action 内完成"写入答案 → 问题状态改为已答 → 追加用户消息 turn → 标记新运行开始"。若问题不是待答状态，原样返回（这就是防双击的机制）。
- **`buildModelContext` 禁止通用拼接**：显式组装，用户答案用固定模板（见 `01-核心协议.md` 第 6 节）。**理由**：现有的 `extractTextContent` 用 `Object.values().join()` 把对象拼成字符串，会把字段名和内部 ID 混进上下文，且字段顺序不稳定——这类 bug 在真实对话里很难被发现。

**判据**
- 乱序事件（`TOOL_COMPLETED` 先于 `TOOL_STARTED`）结果与顺序一致；
- 重复事件（同一 `toolCallId` 两次 `TOOL_COMPLETED`）不产生第二张卡；
- 不属于当前 `runId` 的事件不改变状态；
- 连续两次 `SUBMIT_ANSWER` 只产生一次运行；
- 上下文中不含 reasoning、不含未配对调用、不含 U+200B。

### C2 · `src/hooks/useChatSession.js`

**做法**：`useReducer(reduceSession, 初始值)` + 命令函数。对页面暴露：

```js
{
  // 数据
  turns, pendingQuestion, isRunning, mode, error,
  // 命令
  sendMessage, submitAnswer, skipQuestion, cancelRun,
  retryLastTurn, setMode, openConversation, newConversation,
}
```

要点与理由：

- **每次运行持有自己的 `AbortController`**，存在 ref 里，随 `runId` 一起管理。取消、切换会话、重试时中止上一个。**为什么不放在 `AgentModel` 里**：那里创建控制器无法从外部触达（现状问题）；控制器属于"这次运行"，就应该由分配 `runId` 的一方持有。
- **运行层通过 `onEvent` 回调把事件推给 reducer**。运行层不知道 React 的存在（分层约束），会话层把事件转成 action。
- **`isRunning` 由 `turns.at(-1)?.status === 'streaming'` 派生**，不新增可写布尔量。**理由**：现状的双写问题就是两个可写布尔量造成的；派生状态不可能与真实状态不一致。
- **每个命令都要能安全地重复调用**：`submitAnswer` 依赖 reducer 的原子性；`cancelRun` 在没有运行时是空操作；`retryLastTurn` 在运行中是空操作。

**判据**
- 页面层拿不到任何 `set` 开头的函数（只能发命令）；
- 取消后运行层的 `AbortSignal` 确实被触发（用假运行层断言）；
- `isRunning` 在事件序列的任何时刻都与 `turns` 一致。

### C3 · 测试

**做法**：`node --test`，纯函数测试 + 假运行层驱动的 reducer 测试。

**为什么要有假运行层**：C4 要在 Node 里跑完整闭环，就必须在不联网、不渲染的前提下"播放"一段运行事件。这个假对象很小（按脚本依次调用 `onEvent`），但它让状态机可以脱离网络和界面被验证。

**判据**：C1 的五条 + 双击、取消、迟到事件各有用例，输出可贴。

### C4 · Node 闭环脚本

**做法**：`scripts/session-loop.mjs`，用假运行层驱动 reducer，走完"发送 → 待答 → 作答 → 新一轮"，打印每个 turn 的关键字段。

**为什么在接页面之前做**：这是"协议 + 状态机成立"的独立证据。如果它跑不通，接页面只会让问题更难定位（是状态错还是渲染错）。这一条通过后，D 阶段的界面问题就只可能是渲染问题。

**判据**：打印的两个 turn 内容符合预期，第二个 turn 的上下文里含有第一个 turn 的问题与用户答案，且没有悬空调用。

## 6. 监督与反问

- "迟到事件的处理是返回原状态还是记日志？贴出那段代码。"——要求看到提前返回。
- "如果 `TOOL_COMPLETED` 比 `TOOL_STARTED` 先到，会发生什么？"——要求指出补建分支，或者承认没处理（那就要测出来）。
- "双击作答的防护在哪一行？"——应该在 reducer 的条件判断里，不是在按钮上加 `disabled`（按钮禁用是界面手段，刷新或键盘操作可以绕过）。
- "下一轮的上下文里，学生的答案长什么样？"——要求贴出实际序列化结果，检查有没有 `Object.values` 痕迹。
- "取消之后，如果运行层还是吐了一个事件，会怎样？"——答案必须是不改变状态。

**识别偷工减料**：如果 `useChatSession` 直接返回 `setState` 或者把 reducer 写在组件内部，分层就没有发生，只是换了个文件。如果测试只断言"函数被调用过"，测的是实现细节。

## 7. 遗留风险

- 新旧两套代码短期并存，维护时可能出现"改了新路径忘了旧路径"或反之，需要在验收后尽快下线旧路径。
- 如果端点会返回 SDK 未预期的事件顺序，`toolCallId` 幂等逻辑需要相应放宽；C3 的用例只覆盖已知的乱序情况。
- 时间预算（120s / 45s）与取消的组合行为没有实测。
