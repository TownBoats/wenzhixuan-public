# 阶段 A · 基线与端点验证

估时 1.5 小时｜任务 A1–A4｜产出：依赖对齐、基线存档、端点探针结论｜不写任何产品代码

## 1. 要解决什么

两个必须在这个阶段回答的问题：

1. **我到底在什么依赖上开发？** `package.json` 写 `ai ^6.0.173`，锁文件钉住 `6.0.177`，本机装的是 `6.0.280`；`@ai-sdk/openai` 和 `zod` 同样漂移。今天能调通的 API，未必属于仓库实际锁定的版本。
2. **我配的端点到底支不支持工具闭环？** 这是整个改造的地基。端点若不接受工具参数、或不接受把工具结果回传后继续生成，那么后面五个阶段的工作全部作废。这个事实只能用真实端点验证，mock 测不出来。

## 2. 为什么先做这个阶段

**为什么不能跳过 A3 先写代码**：B 阶段的核心假设是"可以让模型调用工具、并把结果回传后继续生成"。这个假设在标准的 OpenAI 端点上成立，但本项目走的是兼容端点（`createOpenAI({ compatibility: 'compatible' })`），配置默认指向 `open.bigmodel.cn`，模型名却是 `gpt-4o-mini`。兼容层对工具协议的支持程度参差不齐，而且从源码看，这个项目已经在兼容性上踩过坑——`AgentModel` 里那段 `createStreamGateFetch` 就是为了绕开 provider 对 `delta.reasoning_content` 的识别缺陷而写的（详见本节末）。在这种环境里，"应该支持"不是证据。

**为什么用独立脚本而不是在 UI 里试**：UI 里出问题时有三种可能——端点不支持、我们的代码写错、页面状态干扰。独立脚本只有前两种可能，能在一分钟内定位。这个脚本是一次性投资，A3 写完之后，B7 还要用它跑真实端点。

**为什么先对齐依赖**：本机 6.0.280 与锁文件 6.0.177 之间隔了 100 多个补丁版本。如果按本机版本写代码、验证通过，然后按锁文件安装后发现某个 API 不存在，损失的是 B 阶段的工作量。对齐成本是一次 `pnpm install`。

**为什么不借机升级**：升级会同时引入"新版本行为变化"和"我们写的代码有 bug"两个变量，两天窗口内不值得。而且旧路径（`ChatPage`）现在能跑，升级要连带回归它。只有当 6.0.177 存在阻塞性缺陷时才升级，并且要单独记录原因和影响面。

## 4. 任务清单

### A1 · 依赖对齐

**做法**：在项目根目录执行 `pnpm install --frozen-lockfile`，然后读取三个包的实际版本。

**为什么用 `--frozen-lockfile`**：它会拒绝在锁文件与 `package.json` 不一致时修改锁文件，从而保证"安装结果 = 仓库声明的状态"。如果它报错，说明锁文件本身有问题，那是必须先解决的事。

**判据**
- `ai`、`@ai-sdk/openai`、`zod` 的实际版本等于锁文件记录值（`6.0.177 / 3.0.63 / 4.4.3`）。
- `git status` 显示 `package.json` 和 `pnpm-lock.yaml` 无改动。
- 在锁定版本的类型声明里确认存在：`stopWhen`、`stepCountIs`、`tool`、`jsonSchema`、`maxOutputTokens`、`maxRetries`、`ai/test` 的 `MockLanguageModelV3`、`@ai-sdk/openai` 的 `parallelToolCalls`。

**为什么判据里要"确认存在"而不是"能 import"**：类型声明能证明 API 属于这个版本；import 成功只证明运行时不报错，可能是从传递依赖里解析到的别的东西。

### A2 · 基线存档

**做法**：依次执行 `npx vite build`、`npx eslint .`，保存原始输出。人工在浏览器里走查旧路径 6 项行为：普通发送、等待提问、选择五档答案作答、自己输入作答、切换历史会话、重试上一条。

**为什么要人工走查而不是只跑命令**：本次改造要替换的正是这条路径的行为。你现在看到的"正常"，就是验收时的对照标准。特别是这几处容易被忽略的现状：一轮可能同时出现两个问题卡；作答后界面会自动发起下一轮（由 effect 触发）；作答内容以独立的答案卡出现在界面上，但不进入模型上下文。

**判据**
- build 成功，记录主包体积；eslint 输出记录错误/警告数量。
- 6 项行为各有"正常/异常"的记录，异常项写明现象。
- 形成一份"已存在问题清单"，明确哪些不属于本次引入。

### A3 · 端点探针

**做法**：新建 `scripts/probe-tools.mjs`，从环境变量读取配置（`PROBE_BASE_URL` / `PROBE_API_KEY` / `PROBE_MODEL`），跑五个用例并打印结果。

**为什么要写成独立脚本而不是测试**：它需要真实网络和真实密钥，不适合进测试套件；而且它要能在任意端点上重复运行，输出给人看。脚本不进 `src/`，不会被 Vite 打包。

**五个用例**

| # | 用例 | 验证什么 | 结果怎么算通过 |
| --- | --- | --- | --- |
| ① | 单个工具调用 | 端点是否接受工具定义，模型是否返回结构化参数 | 打印出工具名和参数对象（不是正文里的 JSON 文本） |
| ② | 工具结果回传后继续生成 | 多步循环是否成立——这是 B 阶段的核心假设 | 第二步产生新的文本输出，步数为 2 |
| ③ | 思考模型 + 工具 + 第二步 | `reasoning_content` 不进协议消息的风险 | 第二步不报 400；打印出 `response.messages` 的实际结构 |
| ④ | 开闸标记检查 | 确认它确实进入了协议消息 | 打印 `response.messages`，确认文本块里是否出现零宽空格 |
| ⑤ | `parallelToolCalls: false` | 该选项是否被接受 | 请求成功；若报错，记录为"端点不支持，必须靠应用层去重" |

**为什么用例③要单独测**：`@ai-sdk/openai` 的 chat provider 不识别 `delta.reasoning_content`，本项目是靠原始 chunk 手动提取来显示的。这意味着模型返回的思考内容**不会**出现在协议消息里。有些厂商要求在同轮的多步工具调用中把思考内容回传，否则拒绝请求。本方案的设计是"提问成功后立即停止"，大多数轮次只有一步，所以风险较低——但参数校验失败、让模型修正的那一步就可能撞上。如果③失败，对策是改用 `@ai-sdk/openai-compatible` 或厂商专用 provider，这属于 B 阶段开工前就要知道的事。

**为什么用例⑤不能跳过**：不能用"端点会忽略这个选项"来假设。得知道它是否被接受，才能判断应用层的去重是"锦上添花"还是"唯一防线"。

**判据**：五个用例各有明确的通过/失败/不支持结论，附原始输出（密钥需打码）。至少 ① 和 ② 通过才算 A 阶段通过。

### A4 · 结论入档

**做法**：把 A1–A3 的结果写进 `docs/agent-mvp/决策记录.md`，包括：锁定的依赖版本、端点与模型、五个用例结论、旧路径基线、遇到的不确定项。

## 6. 监督与反问

拿着这几条去问 AI（或自问）：

- "用例②通过时，你是怎么确认**第二步确实发生了**，而不是模型在第一步就把话说完了？"——要求出示步数或两次生成的原始片段。
- "`response.messages` 里开闸标记的处理结论是什么？是'没有出现'还是'没有检查'？"——这两者完全不同。
- "依赖实际装的是哪个版本？请贴出打印版本的命令和输出。"——不接受"已经按锁文件安装"这种描述。
- "旧路径的第 3 项行为（选择答案作答）你实测的结果是什么？"——要求具体现象，不接受"看起来正常"。

**识别偷工减料**：如果这一阶段结束时你只得到了"依赖已对齐、端点支持工具"，而没有真实的原始输出和版本号，那么它就是走过场。本阶段的全部价值在于**证据**，不在于结论语句。

## 7. 已知风险

- 演示端点通过，不代表所有 OpenAI 兼容端点都通过。这个限制要写进决策记录。
- 思考模型可能需要换 provider 实现（`@ai-sdk/openai-compatible` 或厂商专用），换 provider 会牵动 `AgentModel` 里那段开闸逻辑——它需要在新适配器里被重写，不能照抄。
- 免费额度的端点在演示过程中可能限流，属于产品外的风险，不在方案内解决。
