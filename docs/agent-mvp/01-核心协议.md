# 01 · 核心协议（唯一事实源）

> 2026-11-01 归档说明：下文是 A–G 期间的历史协议，标题与正文保留当时语境，不再作为现行实现的唯一来源。原文快照见 [历史协议](../archive/agent-upgrade-2026-11-01/agent-mvp/01-核心协议.md)，当前三工具、参数流式事件和结构化候选服务见 [现行业务知识](../knowledge/agent-upgrade.md)。

本文件定义跨阶段共用的数据结构与协议。任何阶段需要改动它时，先改这里，再改代码。总纲 `docs/AGENT_MVP_PLAN.md` 第 4 节是摘要，冲突时以本文件为准。

## 1. 为什么先定协议

这次改造要解决的问题是"谁决定下一步"。当前实现里，决定下一步的是页面中的标签解析器和 effect；改造后，决定下一步的是模型发出的工具调用，加程序设定的停止条件。这两者的差别是一条**协议**，不是一段界面代码：

- 模型想提问时，通过一个有名有参的调用表达意图，而不是在正文里写 `〖question〗`。
- 程序负责校验参数、执行副作用（调用副模型）、把结果按协议回给模型。
- "该停了"由程序判断，并反映为一个明确的状态。

协议先定，代码才有可对照的标准；协议不定，B、C、D 三个阶段会各自发明一套，最后在页面上对不上。所以本文件先写，并且要写清每一处"为什么这样定"。

## 2. `ask_question` 工具

### 2.1 输入

用 `jsonSchema()`（理由见 2.4）声明，拒绝未知字段。

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `question` | string | 去空白后 1–500 字符 | 给学生看的问题，一个问题只包含一个主题 |
| `context` | string | 可选，≤2000 字符 | 生成候选答案所需的有限教学上下文，例如"学生已了解函数作用域" |

模型**不能**传入：问题 ID、密钥、端点、任意函数名、参考答案。问题 ID 由程序生成。

**为什么限制成两个字段**：schema 的可表达能力越弱，模型的越界空间越小，程序要校验的分支也越少。长度上限是产品约束不是技术约束（首期取值可按演示样例调整），但要写进代码，不能只写在提示词里——提示词是建议，schema 和校验才是约束。

**为什么 `context` 不由程序自动从页面状态取**：当前实现隐式依赖"主模型上一段正文"作为副模型上下文（`ChatPage.jsx` 里用 `currResponseRef` 拼）。这种隐式耦合会让副模型看到的内容随页面渲染时机变化，无法测试。改为由主模型显式给出它认为必要的上下文，行为可复现。

### 2.2 执行流程

```text
以 toolCallId 去重：同一 toolCallId 已有执行记录 → 直接返回上次结果（不再校验，幂等优先）
校验参数
  └─ 模式不是 socratic         → rejected('mode_not_allowed')
  └─ 字段非法（长度/未知字段）  → rejected('invalid_input', 说明)
  └─ 本轮已问过相同文本的问题   → rejected('duplicate_question')
  └─ 执行中出现程序错误         → rejected('internal_error', 说明)
未配置副模型                 → { status:'ready', optionsStatus:'unavailable',
                                 errorCode:'option_model_not_configured', nextAction:'await_user' }（不发起调用）
调用 generateAnswerOptions({ question, context, language, abortSignal })
  └─ 至少一条可识别档位        → { status:'ready', optionsStatus:'ready', nextAction:'await_user' }
  └─ 失败/超时/零条可识别档位   → { status:'ready', optionsStatus:'unavailable',
                                 errorCode:'option_model_failed', nextAction:'await_user' }
返回结果（不等待学生！）
```

**为什么失败也返回 `ready`**：问题的价值不依赖候选答案。副模型挂了，学生仍能看到问题并直接作答，教学继续；如果返回错误，这一轮就白跑了。降级比失败好，但降级必须能被看见——`optionsStatus` 会渲染成"候选答案生成失败，可以直接输入回答"，不会显示成空白的成功状态。

**为什么 `execute` 绝不等待学生**：等待会让一次工具调用悬在内存里，刷新即丢失，且模型无法区分"学生想了很久"和"卡住了"。学生的回答在语义上是**下一轮的 user 消息**，不是工具结果。这一条是整个设计的支点：工具结果的含义是"问题数据已准备好"，仅此而已。

**为什么用 `toolCallId` 去重**：网络重试、并行调用、双击都可能让同一调用被执行两次。去重让"同一个 ID 只产生一张卡片"成为协议保证，而不是界面补丁。**去重必须排在所有校验之前**：否则重放的那一次会先命中"本轮已问过这段文本"被判 `duplicate_question`，永远走不到"返回上次结果"，幂等就失效了。

**为什么程序错误也返回 `rejected`**：工具执行里抛异常会让 SDK 产生 `tool-error`，模型看到的是异常而不是结构化结果，界面也只能显示失败卡。程序错误（配置缺失、依赖抛错）应如实标注为 `internal_error`，**但不能把异常原文回给模型**（异常里可能带端点、请求头）——`message` 只允许固定文案。

**为什么一轮允许多个问题**：产品是"探针"式教学——一次用多个问题同时探测学生的水平，逐个提问体感太慢。所以程序**不设问题数量的硬上限**：每轮问几个由教学指令软引导（建议 2–3 个，见 `skills/socratic.md`），代码不拦截。数量上真正起作用的约束只有三条：步数上限、`toolCallId` 去重（同一调用只执行一次）、文本去重（同一轮不重复问同一句话）。**为什么不用硬上限**："该问几个"取决于教学内容，硬编码会把本可一次问清的内容逼成多轮；软引导能表达偏好，又不会在边界上把教学意图判为非法。

**为什么副模型并发上限是 4**：每个问题各需一次副模型调用，每次都是秒级耗时。串行会让一轮耗时随问题数线性增长，与"探针要快"直接冲突；并发过高则会撞端点限流、也让主运行 120s 预算被摊薄。取 4 为上限、超出的排队；每个调用仍受 45s 与主运行剩余时间双重约束，且**失败隔离**——某一个失败只影响它自己的 `optionsStatus`，其余问题照常就绪。

### 2.3 结果结构

```js
// 成功：至少一条
{ status:'ready', questionId:'q_...', question:'…？',
  options:[{ level:'none'|'heard'|'basic'|'familiar'|'expert', text }, …],  // ≥1 条，不是固定 5 条
  optionsStatus:'ready', nextAction:'await_user' }

// 降级：问题可用，候选答案不可用
{ status:'ready', questionId:'q_...', question:'…？',
  options:[], optionsStatus:'unavailable', errorCode:'option_model_failed', nextAction:'await_user' }
// errorCode 两种取值：'option_model_not_configured'（未配置副模型，不发起请求）
//                    'option_model_failed'（已配置但调用失败 / 超时 / 零条可识别档位）

// 拒绝：重复提问 / 模式不允许 / 参数非法 / 程序错误
{ status:'rejected', reason:'duplicate_question', message:'可选说明' }
// reason ∈ 'duplicate_question' | 'mode_not_allowed' | 'invalid_input' | 'internal_error'
```

拒绝也必须是**合法返回**，因为模型可能在同一响应里请求多个调用。每一个调用都要有配对结果，否则下一次请求的上下文里有悬空的 tool call。

**一轮里可以有多个问题**：每个成功调用产生一条独立的问题结果与一张卡片，`questionId` 逐个生成、互不复用；问题顺序就是模型调用顺序，界面按这个顺序展示。所以 turn 里保存的是**问题数组**（第 5 节），不是单个问题。

**为什么候选答案不要求五档齐全**：五档是给学生自评用的水平梯度，缺一两档时学生仍可手输或跳过；把缺档判成整轮不可用，会让副模型的一次轻微偏差直接清空全部候选答案（界面只剩输入框）。所以口径是「有多少档显示多少档，每条必带档位」，真正算失败的只有**零条可识别档位**。同一档出现多次时只保留第一条（避免同一屏两个「基本了解」），档位顺序固定为 `none → heard → basic → familiar → expert`。

### 2.4 schema 用 `jsonSchema()` 而不是 `zod`

| | 推荐：`jsonSchema()` | 替代：`zod` + `zodSchema()` |
| --- | --- | --- |
| 理由 | `zod` 不是本项目的直接依赖，只是 `ai` 的 peer 依赖被装上；靠 node_modules 里恰好存在来 import，是运气不是契约 | 声明式校验、错误信息友好 |
| 代价 | schema 只做形状声明，语义约束（长度、去空白、未知字段）由我们自己的校验函数负责；错误信息要自己写 | 需要在两天窗口内改 `package.json` 和锁文件，并重新验证与 `ai@6.0.177` 的兼容 |

选它的前提是：**不做把校验交给 schema** 这件事。`execute` 里必须有一段显式的校验函数，schema 只是为了告诉模型参数长什么样。如果将来要加 `zod`，改动只在这一个文件里，边界清晰。

## 3. 停止条件

```js
// 示意；steps 中每个 step 的 tool 结果字段名以 A1 在锁定版本上的复核为准
const askQuestionReady = ({ steps }) => {
  const last = steps.at(-1)
  const results = last?.toolResults ?? last?.content?.filter(p => p.type === 'tool-result') ?? []
  return results.some(r =>
    r.toolName === 'ask_question' && r.output?.nextAction === 'await_user')
}

const stopWhen = [stepCountIs(3), askQuestionReady]
```

**为什么不用 SDK 的 `hasToolCall('ask_question')`**：它在"模型调用了这个工具"时就停，包括参数非法、被拒绝的那些情况。那样模型就没有机会修正参数，方案里"预算内允许修正一次"直接失效。停止条件要表达的是业务判断"问题已经准备好，该等人回答了"，而不是"出现了某个名字的调用"。

**为什么两个条件并列**：`stepCountIs(3)` 是安全上限（防跑飞），`askQuestionReady` 是正常出口。只有业务出口没有上限，模型行为异常时会烧掉预算；只有上限没有业务出口，就退化成固定三步的流程，失去了让模型自己决定何时提问的意义。

**多个问题时怎么算就绪**：只要**任一**结果带 `nextAction:'await_user'` 就满足 `askQuestionReady`——工具已经执行完、问题数据已经就绪，不需要等"全部成功"。同一步内的多个调用由 SDK 一并交出结果，因此不会出现"先返回的那个把循环停掉、其余调用没有结果"的情况。

## 4. 规范事件

运行层把 SDK 的流翻译成下面这组事件，交给会话层。事件是运行层唯一的输出形式，页面不接触 SDK。

| 事件 | 数据 | 用途 |
| --- | --- | --- |
| `run-started` | conversationId, turnId, runId, mode | 固定本轮配置，初始化状态 |
| `text-delta` | runId, partId, delta | 追加到指定正文片段 |
| `reasoning-delta` | runId, partId, delta | 展示接口真实返回的推理内容 |
| `tool-started` | runId, toolCallId, toolName, input | 创建执行中的工具卡 |
| `tool-completed` | runId, toolCallId, output | 更新同一张卡与问题数据 |
| `tool-failed` | runId, toolCallId, error | 展示失败或降级说明 |
| `run-finished` | runId, reason, responseMessages | 提交协议消息与结束状态 |

`reason ∈ completed | awaiting_user | failed | cancelled | limit_reached`。

**为什么每个事件都要带 `runId`**：会话可能在运行中被切换、取消或重试。迟到的流片段如果只带文本，接收方无法判断它属于哪一次运行，只能照着往里写——这正是当前实现里"旧流污染新会话"的根因。身份信息比状态标志可靠：`isLoading` 是布尔值，无法区分"哪个运行"；`runId` 可以。

**为什么工具状态和问题状态分开**：工具可能已完成（问题和候选答案都准备好了），而问题仍在等待学生。把两者合并成一个状态，就无法表达"卡片已完成、但流程还在等"这个最常见的中间态。

## 5. Turn 记录

一个会话由有序的 turns 组成，每个 turn 保存同一份数据的两种投影：

```js
{
  id, runId, modeSnapshot,          // 'normal' | 'socratic'，本轮固定
  status,                           // streaming | awaiting_user | completed | failed | cancelled | interrupted
  userMessage,                      // { text, source:'input'|'answer', questionId?, selectedLevel? }
  modelMessages: [],                // 清洗后的 SDK 协议消息（assistant/tool 配对），回传给模型用
  parts: [],                        // 有序展示片段：{ type:'text'|'reasoning'|'tool', … }，渲染用
  questions: [],                    // 数组，一项对应一次 ask_question 调用：
                                    // { toolCallId, id, text, options, optionsStatus,
                                    //   answer, state: 'pending' | 'answered' | 'skipped' }
                                    // 顺序＝模型调用顺序
  error: null,                      // 可展示的失败原文（清洗过，不含端点密钥）
  errorKind: null,                  // 'timeout' | 'failed' | null，失败类别（F3）
}
```

**为什么需要 `errorKind`**：运行层用 `endedBy` 区分「超时」与「其他失败」，但它只活在返回值里；会话层把错误压成一行 `message` 后，「超时」与「取消」在旧实现里是同一句「运行已中断」，界面无法分类。所以由运行层在错误对象上打 `endedBy` 标记，会话层把它存成 `errorKind`（取消一律为 `null`，因为取消不是错误）。它只用于展示与排查：**不进模型上下文、不影响任何协议判断**；`null` 表示没有可分类的失败。

**为什么要同时保留两种投影**：只把工具卡加进界面记录、却只把最终文本回传给模型，模型就看不到自己发起过什么调用、拿到了什么结果，会重复提问或否认自己问过。反过来，把协议消息直接渲染，界面就得理解 SDK 的数据结构。两种需求是真实的，所以保留两种表示，但**由会话层统一更新**——这是它与现状最大的差别：现状是 `messages` 和 `uiMessages` 两个 state 各自能被修改，已经出现内容分叉（作答摘要进了 `messages` 却没进 `uiMessages`）。

**为什么 `modelMessages` 要清洗**：至少三件事必须做——去掉开闸标记（U+200B，`AgentModel` 注入的）、保证调用与结果配对、不把 reasoning 当成模型说过的话回传。清洗只在一个地方做（运行层的适配器），下游拿到的就是干净的。

## 6. 模型上下文

由已完成 turns 的 `userMessage` 和 `modelMessages` 按顺序组成。

**禁止**：用 `Object.values(...).join(...)` 之类的通用拼接把对象变成文本（当前 `chatMessages.js:extractTextContent` 就是这么做的），因为那会把字段名、内部 ID 甚至配置泄露进上下文，且顺序不确定。

用户答案用固定模板序列化，一轮的多个答案按问题顺序连续排列，例如：

```text
针对问题「<问题原文>」，我的回答是：<答案正文>
（来自选项：basic / 熟练）

针对问题「<问题原文2>」，我的回答是：<答案正文2>
（来自选项：自定 / 手动输入）

针对问题「<问题原文3>」：（学生选择了跳过，未作答）
```

**为什么把"来自选项"也写进去**：模型需要知道这是学生从候选中选的，还是自己写的，才能把握反馈的语气。但"选了精通"只是学生自评，不能记录成"已掌握"——这条要写进教学提示词，避免模型据此跳过基础。

**为什么一轮的几个答案一起进入上下文**：一轮的问题是一个整体（探针一次探测几个维度），全部答完或显式跳过后才发起下一轮。跳过必须写成**显式**的一条记录，不能留缺口——否则模型会把"没有回应"误读成默认同意或沉默。

## 7. 存储格式（v2）

新键 `chat_histories_v2`，值为会话数组：

```js
{
  id, title, timestamp, schemaVersion: 2,
  mode,                                  // 最近一次使用的模式
  turns: [ /* 上面第 5 节的 turn，去掉函数与不可序列化字段 */ ],
}
```

**为什么用新键而不是在同一数组里混存版本**：localStorage 的写入是覆盖式的。混存需要读全量、改一条、写回全量，任何一次并发或异常都可能损坏用户已有的数据；分键之后旧键只读，写入天然隔离。代价是删除和重命名要处理两个键，这个代价明显小于数据损坏。

**禁止入库**：函数、`AbortController`、`apiKey`、`endpoint`、reasoning 原文、开闸标记。

## 8. 协议不变量（验收时逐条检查）

1. 每个 tool call 都有配对的 tool result，运行结束时不存在悬空调用；
2. 协议消息与展示文本中都不含开闸标记（U+200B）；
3. reasoning 不出现在模型上下文里；
4. 学生的回答只以 user 消息进入下一轮，且同一答案只提交一次；
5. 同一 `toolCallId` 只产生一张卡片和一次执行；
6. 每个事件带 `runId`，不属于当前运行的事件被丢弃；
7. 依赖以 `pnpm-lock.yaml` 为准。
