# 阶段 D · 页面接入、模式与设置迁移

估时 2.5 小时｜任务 D1–D8｜依赖 C 通过｜产出：浏览器里走通"输入 → 工具卡 → 问题与五档 → 作答 → 反馈"，并用显式模式取代提示词猜测

## 1. 要解决什么

让已经成立的协议和状态机在真实界面上可见、可操作，同时处理三件与现有设置相关的历史遗留：

1. **模式靠提示词猜**：`AgentConfigPanel.findModeByPrompt` 拿当前提示词的**全文**去比对内置提示词，以此来显示"当前是哪个模式"。改了提示词、换了语言、或提示词被语言切换逻辑写回 localStorage，模式显示就失准。
2. **老用户的提示词与新协议冲突**：`mainAgentPrompt` 保存的是**完整系统提示词**，其中包含 `〖response〗/〖question〗` 标签规则。如果照旧把它拼进系统提示，模型会同时收到"用标签提问"和"用工具提问"两套指令。
3. **配置门槛过严**：`ChatPage.isModelConfigured` 要求主、副模型都配置好才能开始，导致只想普通聊天的用户被拦在门外。

## 2. 为什么这样做

### 2.1 为什么模式必须由代码保证，而不是由提示词声明

提示词是建议。用户可以在设置里改写它（现状就允许），模型也可能不完全遵守。而"当前是哪个模式"决定三件**程序行为**：注册哪些工具、工具和停止条件怎么配置、界面进入什么状态。这些不能依赖一段文本。

做法：
- 模式是一个显式设置值（`teaching_mode: 'normal' | 'socratic'`），随会话和每个 turn 快照保存；
- 模式控件直接读写这个值，不再比对提示词；
- 每个 turn 保存 `modeSnapshot`，这样历史记录能显示"这一轮是在什么模式下进行的"，即使全局模式后来变了。

**为什么快照要存在 turn 上而不是会话上**：用户在会话中途切换模式是允许的（下一轮生效）。只存一个会话级模式，历史就说不清某一段回答属于哪个模式。

### 2.2 提示词迁移：为什么忽略而不是拼接

| | 推荐：内置提示词直接忽略，自定义提示词不自动拼接 | 替代：把用户提示词作为"教学偏好"追加 |
| --- | --- | --- |
| 协议安全 | 旧提示词里的标签规则不会进入系统提示 | 同一份提示词里同时存在标签协议和工具协议 |
| 用户预期 | 需要一次明确的提示（"自定义提示词在新模式下暂不生效"） | 用户感觉自己的设置还在 |
| 可回归 | 系统提示只由代码生成，可以写单元测试 | 最终提示词依赖用户本地存储，难以测试 |

**为什么判定要覆盖中英文两份内置提示词**：`SYSTEM_PROMPTS.LEARNING_MODE` 从 `localStorage.learning_mode_prompt` 取缓存值，而 `prompts.js` 在语言切换时会把**当前语言的**译文写回该键。所以用户机器上存下来的值可能是任一语言的版本，也可能恰好等于内置值。

**判定规则**：存储值与"中英任一份当前内置提示词的原文"完全相等 → 视为未自定义，忽略；否则视为已自定义 → 不拼接，在设置页显示提示。

**为什么是"完全相等"而不是模糊匹配**：模糊匹配会误判用户真正改过的提示词（例如只改了一个词的教学要求），那样会静默丢弃用户的内容。宁可让少数"改过但很接近"的用户看到提示，也不要静默改变行为。

### 2.3 为什么常规模式不要求副模型

工具只在苏格拉底模式注册（B2）。常规模式根本不调用副模型，却因为一个全局的 `isModelConfigured` 而无法使用，是纯粹的门槛错误。改动很小，但它直接影响演示成功率——演示时少一个可能没配好的依赖。

### 2.4 为什么工具卡要单独做一个组件

工具执行过程是本次改造最值得展示的部分（也是简历表述里的"工具过程展示"）。它有三个与普通消息不同的地方：有生命周期（执行中 → 完成/失败）、有可展开的细节（参数、结果）、失败时不能整块消失（否则用户会以为什么问题都没发生）。这些差异用一个独立组件表达，比在 `MessageBubble` 里加分支更清楚。

**为什么状态不能只靠颜色**：执行中/完成/失败三态要用文字和图形区分。这是可访问性要求，也让截图和面试讲解更清楚。

**为什么 `ThinkingBlock` 只显示接口真实返回的 reasoning**：现在有些项目会生成"模拟思考过程"。这个项目有真实推理流（`reasoning_content`），一旦开始显示编造的内容，用户就无法分辨哪部分是模型真的在推理。推理与工具日志要分开标识——前者是模型的自述，后者是可验证的执行记录。

## 3. 需要你决策的点

### 决策 1：新界面的模式选择放在哪里

| 选项 | 说明 | 代价 |
| --- | --- | --- |
| A. 头部切换控件（推荐） | 与现有 `HeaderButtons` 同排，随时可见可切 | 头部已有新对话/设置/侧边栏等按钮，稍显拥挤 |
| B. 放在设置面板 | 与现有 Agent 提示词配置同处 | 需要打开设置才能切换，演示时多两步 |
| C. 发送框上方 | 靠近输入，切换成本低 | 与现有布局风格差异较大 |

**倾向 A**：模式影响每一次发送，应该常驻可见。而且现有的 `AgentConfigPanel`（设置里的模式下拉）在本次改造后职责会变成"编辑教学指令内容"而不是"选择模式"，两件事分开更清楚。

需要你定：`AgentConfigPanel` 里的模式下拉是保留（作为提示词编辑器入口）还是一并移除？**倾向保留但改名**，因为它承载着用户查看/修改提示词的能力。

### 决策 2：工具卡展开后显示什么

工具卡是给用户看过程、给你看调试的，两者需要的详细程度不同。

| 选项 | 说明 |
| --- | --- |
| A. 默认折叠，展开显示：工具名 + 输入的问题 + 执行结果摘要（倾向） | 用户视角友好 |
| B. 默认折叠，展开显示完整 JSON | 调试方便，但界面上会出现技术噪声 |
| C. 开发模式开关控制详细程度 | 最干净，但需要接上现有的 `useDeveloperMode`，多一处状态 |

**倾向 A**，并在 F 阶段验收时确认错误/降级信息在展开内容里可见（验收清单要求"错误可见"）。

### 决策 3：正常链路之外，失败时说什么

方案要求失败可见，但文案需要你确认口径。需要覆盖四种：副模型失败（问题仍在，可手动输入）、端点不支持工具（建议切换到常规模式）、保存失败（对话保留在内存）、运行被取消。倾向直接用中文短句、不出现技术术语（例如不说 "tool call"），详细原因放在展开区。

## 4. 任务清单

### D1 · `App.jsx` 增加运行时开关

**做法**：读取 `localStorage.agent_runtime`，为真时渲染 `AgentChatPage`，否则渲染现有 `ChatPage`。开发期默认关。

**为什么默认关，而不是默认开**：在 F 阶段验收通过之前，默认开等于把未验收的路径当作产品默认行为，一旦出问题，18 日就没有可投递的版本。默认关意味着"开关是新路径的唯一入口"，回退成本是零。

**为什么用 localStorage 而不是代码常量**：验收和演示时需要能立即切换，不需要改代码、重新构建。

**判据**：开关为关时，`vite build` 产物与改动前行为一致（人工走查旧路径 6 项行为）。

### D2 · 模式控件

**做法**：头部增加模式切换；读写在 `teaching_mode`；`derivedViewState.canChangeMode` 为假时禁用。

**为什么运行中或有待答问题时禁用**：切换模式会改变工具注册和教学指令，正在跑的那一轮用的是旧快照，改了会让人以为当前这轮也变了。待答问题则是因为切换后"该由哪个模式来处理这个答案"没有答案——方案原打算把旧问题标记为失效（`superseded`），首期为了减少状态组合改为禁用。这个取舍要写进决策记录。

**判据**：禁用时给出可读原因（不只是变灰）；键盘可操作；切换后下一轮生效。

### D3 · `MessageContent` 与 `ToolCallCard`

**做法**：`MessageContent` 按 `parts` 顺序渲染文本、推理、工具；`ToolCallCard` 覆盖四态（准备问题中 / 生成候选答案中 / 完成 / 候选答案不可用）。

**为什么按 `parts` 顺序渲染而不是把工具卡统一放在末尾**：模型可能是"先说一句 → 调用工具 → 再说一句"。统一放末尾会让界面顺序与实际发生顺序不一致，用户会以为模型先说完才提问。这是 `01-核心协议.md` 里保留有序 `parts` 的直接原因。

**判据**：同一 `toolCallId` 不会出两张卡；展开可键盘操作并有明确展开状态；四态各有可识别的文案。

### D4 · 本轮问题卡组 `QuestionCard` + `AnswerCard`

**做法**：复用现有组件，传入 `turn.questions`（本轮全部问题，按模型调用顺序）；作答走 `submitAnswer`，三条路径：选项作答、自定义输入、**跳过**。

**为什么复用而不是重写**：现有的 `QuestionCard` 和 `AnswerCard`（591 行）承载了实际调整过的交互（层级、选中态、关闭行为）。重写会引入一轮样式返工，而本次改造的验收项不包含界面重设计。

**与现状的关系**：现状一轮会出现多个问题卡、面板显示"共 N 题"；新路径**保留一轮多问题**（探针式教学要一次探测多个维度，见 `决策记录.md` B-3），差别在于由 turn 状态驱动、顺序确定、**卡片数＝问题数且无重复卡**（协议不变量 5），并新增"跳过"路径。

**为什么"跳过"不能省略**：一轮的问题要么答完、要么显式跳过，本轮才结束并进入下一轮；漏掉的问句会变成上下文里的缺口，模型会误读为默认同意（`01-核心协议.md` 第 6 节）。

**判据**：选项作答、自定义作答、跳过三条路径都能让本轮完成并进入下一轮；答案卡展示的层级与文案与实际选择一致；卡片数与问题数一致；**候选答案按 `options.length` 渲染，不得硬编码 5 行**（`决策记录.md` B-10 放宽了档位数量，缺档时界面只显示实际存在的档位）。

### D5 · 配置门槛调整

**做法**：无工具兜底模式（代码层保留、界面不暴露，见 `决策记录.md` B-1）**只在端点不支持工具时由程序启用**，它只校验主模型；苏格拉底模式缺副模型时**不切换模式**，而是提示配置并允许以手动回答继续（`optionsStatus: 'unavailable'`、`errorCode: 'option_model_not_configured'`，见 `决策记录.md` B-6）。

**为什么"缺副模型"要允许继续而不是阻断**：学生会话的价值在于对话本身，候选答案只是辅助。阻断会让一个没配副模型的用户完全无法使用苏格拉底模式，而降级路径已经存在（B3/B4 已实现）。

**判据**：只配主模型时，苏格拉底模式给出可读提示（指向设置）且能手动作答，**不切换模式**；端点不支持工具时程序降级到无工具兜底模式并说明原因。

### D6 · 提示词迁移判定

**做法**：`src/utils/promptMigration.js`（或并入 `conversationState.js`）导出判定函数；设置面板显示相应提示。

**为什么单独成文件并写单元测试**：这是"静默改变用户行为"的地方——判错了会丢掉用户改过的提示词，或者让旧协议漏进系统提示。静默的错误必须有测试兜住。

**判据**：中英文内置提示词、语言切换写回的缓存值都判为"未自定义"；用户改过一个词的值判为"已自定义"。

### D7 · 文案（zh / en）

**做法**：新增键写入 `src/locales/{zh,en}/translation.json`。

**为什么放到最后**：文案依赖 D2–D6 的最终形态。**可裁剪**：时间不够时先只做中文，英文缺失键不影响演示（但要在决策记录里写明）。

### D8 · 真实端点浏览器闭环走查

**做法**：`agent_runtime` 打开，用同一个教学主题（例如闭包）走正常链路和失败链路，并在窄屏下检查工具卡。

**为什么规定同一个主题**：跨阶段用同一主题便于前后对比（A 阶段基线、B7 单跑、D8 界面、F 验收都用它），出现差异时容易判断是哪一层引起的。

**判据**：正常链路完整走通；失败链路（副模型不可用/端点不支持工具）有可读提示且不卡死；窄屏工具卡可读。

## 5. 验收证据

1. `agent_runtime` 关闭时的旧路径走查记录（6 项行为）。
2. 正常链路的截图或逐步记录：工具卡执行中 → 完成 → 问题卡 → 作答 → 反馈。
3. 失败链路的记录：副模型不可用时的界面表现。
4. D6 的单元测试输出。
5. 窄屏截图。
6. 改动文件清单：确认未修改旧 `ChatPage`、`StreamingParser`、`AgentModel`。

## 6. 监督与反问

- "模式控件是怎么知道当前模式的？"——答案必须是读显式设置值。如果代码里又出现"拿提示词比对"，D 阶段的核心目标就没达成。
- "工具卡会不会出现在回答末尾，而不是它实际发生的位置？"——要求贴出 `parts` 渲染逻辑。
- "老用户那条含标签规则的提示词，现在会不会发给模型？"——要求指出判定函数，并跑那次单元测试。
- "只配主模型时，常规模式能开始对话吗？"——现场试一次。
- "一轮里能出现两个问题吗？"——要求明确回答，并说明产品行为变化是否已记录。

**识别偷工减料**：如果在 `MessageBubble` 里加了一段 `if (type === 'tool')` 就算完事，而没有处理 `parts` 顺序，那卡片位置会错。如果只做了中文文案却说"i18n 已完成"，要指出英文键缺失。

## 7. 遗留风险

- 一轮一题是产品行为变化，需要你确认；现有用户的历史里仍会有多题卡片（E 阶段只读投影要能显示）。
- 模式控件在窄屏下与现有头部按钮可能拥挤，需要实际检查。
- 自定义提示词的用户会失去个性化设置（有提示但不自动迁移），这是本期接受的代价。
