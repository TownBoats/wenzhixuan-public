# 问知轩 Agent MVP 开发规则

本项目的 Agent 改造有完整方案文档，并以 `docs/agent-mvp/HANDOFF.md` 跨会话交接进度。**先读交接文件确认进度，再读方案文档，最后才写代码**；不要凭常识补全设计，也不要凭记忆判断做到了哪里。

## 0. 会话协议：以 HANDOFF 保存开发进度（最高优先）

每一轮对话都是冷启动，你不记得上一轮做过什么。进度只以 `docs/agent-mvp/HANDOFF.md` 为准。

### 0.1 开始时（写任何代码之前）

1. 读 `docs/agent-mvp/HANDOFF.md`，确认：当前阶段、当前任务编号、任务状态、「下一步」、「待你拍板的决策」、「未收尾事项」。
2. 用一句话向用户报告：「HANDOFF 显示当前在 <阶段 · 任务>，状态 <…>，下一步是 <…>」。
3. 核对用户本轮指令与 HANDOFF 是否一致：
   - 一致 → 按第 2 节流程进入该任务。
   - 不一致（用户要做的任务不是 HANDOFF 里的下一步、或跳过了未验收任务）→ **先指出差异并询问**，不要自行选择。
   - HANDOFF 里有与本任务相关的「待拍板决策」→ 先提出，等用户定。
4. 按第 1 节读取本阶段需要的文档。已在 HANDOFF 或决策记录中拍板的结论，**不得重新讨论或推翻**，除非用户主动要求。

### 0.2 结束时（本轮最后一个动作）

无论任务是否完成、是否被中断，都必须按 HANDOFF 末尾的「结束一轮对话前的更新清单」更新它：

1. 第 1 节当前状态；
2. 第 2 节任务状态与证据位置；
3. 第 3 节下一步——具体到任务编号和第一个动作；
4. 第 4 节：新出现的待决策项加进来；已拍板的移到 `决策记录.md` 并从这里删除；
5. 第 5 节未收尾事项（半成品文件、临时代码、已知失败的测试都要写）；
6. 第 6 节本轮改动的文件清单；
7. 第 7 节追加一条会话日志（做了什么 / 证据 / 没做完或卡在哪 / 下一轮从哪开始）。

然后向用户展示 HANDOFF 的改动摘要。

### 0.3 HANDOFF 的书写规则

- **只写事实和证据位置**（命令、文件路径、输出摘要），不写「应该已经可以」「基本完成」之类的推测。
- 任务状态取值：⬜ 未开始｜🟡 进行中｜🔵 待验收｜✅ 完成｜❌ 阻塞｜✂️ 已裁剪。
  - 你完成实施并给出证据后，只能标 **🔵 待验收**；**用户确认验收后才能改为 ✅**。
  - ❌ 阻塞必须写明卡在哪、需要什么才能解除。
  - ✂️ 已裁剪必须在 `决策记录.md` 里有对应记录。
- HANDOFF 回答「到哪了」，`决策记录.md` 回答「为什么」，`01-核心协议.md` 回答「是什么」。**三者不互相复制内容**，只互相引用。
- 会话日志只追加，不改写历史条目。
- 不得在 HANDOFF 中写入密钥、完整端点 URL 中的 token、或用户本地配置。

### 0.4 中途中断

如果本轮无法完成当前任务（超时、端点不可用、等待用户决策），**不要硬做完**。停在一个可描述的状态，把任务标为 🟡 或 ❌，并在第 5 节写清：已改了什么、哪些是半成品、下一轮要先检查什么。

## 1. 文档地图与优先级

| 文件 | 作用 | 何时读 |
| --- | --- | --- |
| `docs/agent-mvp/HANDOFF.md` | 进度交接：阶段、任务状态、下一步、待决策、会话日志 | **每轮开始先读，结束必须更新** |
| `docs/agent-mvp/README.md` | 协作循环、开工提示词、术语、跨阶段约定 | 首次参与或不确定流程时 |
| `docs/agent-mvp/01-核心协议.md` | 数据结构与协议的唯一事实源 | B 阶段起每次开工 |
| `docs/agent-mvp/<阶段>-*.md`（A–F） | 该阶段的问题与约束、方案比较、决策点、任务判据、验收证据、监督反问 | 进入该阶段时 |
| `docs/agent-mvp/<阶段>-开发指导.md` | 该阶段的简版操作步骤 | 进入该阶段时（见 2.3） |
| `docs/agent-mvp/决策记录.md` | 追加式台账：已拍板的结论与理由 | 涉及取舍时 |
| `docs/AGENT_MVP_PLAN.md` | 总纲：目标、代码事实、架构、验收清单 | 需要全局背景或做 F4 验收时 |

**设计层面**冲突时按此顺序取准（上位覆盖下位）：

1. `01-核心协议.md` —— 任何协议改动**先改这里，再改代码**；
2. 阶段文件 A–F；
3. `AGENT_MVP_PLAN.md`；
4. `README.md`。

`决策记录.md` 中**已拍板**的结论优先于以上文档中的「倾向」或「建议」。
**进度层面**只以 `HANDOFF.md` 为准。

文档维护规则：不修改既有文档里已拍板的结论；新结论追加到 `决策记录.md`。确需修正文档（例如发现与源码不符），先说明原因并取得同意，再改，并在决策记录里写一条。

## 2. 分阶段协作流程

### 2.1 顺序

- 阶段 **A → B → C → D → E → F 串行**，不得跳阶段、不得并行开工。上一阶段的检查点未通过（HANDOFF 中未达 ✅），不进入下一阶段。
- 阶段内任务按编号顺序执行（A1…、B1…）。
- **一次只做一个任务编号**。完成即停下、出示证据、把状态标为 🔵、等用户确认后再继续；不得顺手做下一条任务。
- 任务确实必须超出规定范围时，**先列出要改的额外文件并等同意**，不得直接改。

### 2.2 每个任务的固定步骤

1. **复述**：用自己的话说清「要解决什么、约束是什么、完成判据是什么」，并指出不确定或与文档、源码不一致的地方。
2. **列范围**：声明本任务会碰哪些文件、**不会**碰哪些文件。
3. **标注决策点**：阶段文件里「需要你决策的点」**不得自行拍板**。给出选项、倾向、理由，然后等用户定；定下后写入 `决策记录.md`。
4. **实施**：只做这一个任务编号。
5. **交付**：改动文件清单 + 逐条判据的自检结果 + 协议不变量（第 4 节）自检 + 可直接复制的命令与原始输出。
6. **交接**：按 0.2 更新 HANDOFF。

前三步不写代码。讨论和决策的成本是几分钟，协议定错的返工成本是几小时。

### 2.3 阶段开发指导

- 进入新阶段时，若 `docs/agent-mvp/<阶段>-开发指导.md` 不存在，先按 `A-开发指导.md` 的格式起草一份（目标、开工准备、分步操作、每步「你检查」、通过标准、本阶段不要做），**交给用户审阅后再开工**。
- 开发指导是阶段文件的简版，不得引入阶段文件中没有的新设计；发现阶段文件有缺口时，按第 1 节的文档维护规则处理。

### 2.4 阶段收尾

一个阶段的全部任务验收后：

1. 把阶段结论按模板追加到 `决策记录.md`（问题 / 选项 / 结论 / 原因 / 放弃的方案与理由 / 验证证据 / 遗留风险）；
2. 在 HANDOFF 中把当前阶段切到下一阶段，「下一步」写成下一阶段的第一个动作（通常是起草或阅读开发指导）。

## 3. 分层与改动边界

分层职责（不可越界）：

| 层 | 位置 | 硬约束 |
| --- | --- | --- |
| 运行层 | `src/agent/` | **不导入 React、不访问 localStorage、不产生 JSX**。输入＝模式 + 配置快照 + 上下文消息 + `AbortSignal` + `onEvent`；输出＝规范事件 + 清洗后的 `responseMessages` + 结束原因 |
| 会话层 | `src/hooks/useChatSession.js` + `src/utils/conversationState.js` | 分配 `conversationId / turnId / runId`；用 `runId` 丢弃过期事件；统一负责状态归并与投影 |
| 展示层 | `src/components/`、`src/pages/AgentChatPage/` | 只接收数据与回调；**工具卡不执行工具**；不得直接写会话状态 |

本期**允许新增/修改**的文件范围：

```text
src/agent/                        runTeachingAgent.js, modelAdapter.js, modes.js,
                                  skills/{normal,socratic}.md, tools/askQuestion.js,
                                  services/generateAnswerOptions.js, __tests__/
src/hooks/useChatSession.js
src/pages/AgentChatPage/
src/components/{MessageContent,ToolCallCard}/
src/utils/{conversationState,historyStore,promptMigration}.js
src/utils/__tests__/
src/locales/{zh,en}/translation.json   （只新增键，不改已有键）
src/App.jsx                            （仅限加 agent_runtime 开关）
scripts/                               probe-tools.mjs, run-socratic-once.mjs, session-loop.mjs
docs/agent-mvp/HANDOFF.md              （每轮必须更新）
docs/agent-mvp/决策记录.md             （只追加）
docs/agent-mvp/<阶段>-开发指导.md       （按 2.3 起草）
```

**禁止改写**（只允许读取和复用；要复用代码请复制必要片段，不要 import 整个旧实现；`generateAnswerOptions` 按阶段 B 文档可实例化 `AgentModel` 使用）：

- `src/pages/ChatPage/`（含 `ChatPage.jsx`）
- `src/lib/AgentModel.js`
- `src/hooks/useStreaming.js`、`src/utils/StreamingParser.js`

旧路径是保底交付版本，改动它即视为破坏交付。确实必须改时，先写进 `决策记录.md` 并取得同意。

**禁止**：改 `package.json` / `pnpm-lock.yaml`、升级依赖、引入新依赖、引入状态库（Redux/Zustand）、TypeScript 迁移、全站 UI 重设计、后端或 RAG 等总纲第 1 节明确排除的内容。

## 4. 协议不变量（任何阶段都必须成立）

每完成一项任务，逐条自检并写进交付说明：

1. 每个 tool call 都有配对的 tool result，运行结束时**不存在悬空调用**。
2. 协议消息与展示文本中**都不含开闸标记（U+200B）**。
3. reasoning **不进入模型上下文**（只在接口真实返回时展示）。
4. 学生的回答只以**下一轮的 user 消息**进入上下文，且同一答案只提交一次。
5. 同一 `toolCallId` 只产生**一次执行、一张卡片**。
6. 每个规范事件都带 `runId`，不属于当前运行的事件被丢弃（**返回原状态，不报错、不记日志**）。
7. 依赖以 `pnpm-lock.yaml` 为准（`ai 6.0.177`、`@ai-sdk/openai 3.0.63`、`zod 4.4.3`）。
8. 上下文构建只纳入**已配对的、已完成的** turn；未配对调用留在 `parts` 里展示与诊断，但不发送。

## 5. 禁用清单（出现即判定未完成）

| 禁止 | 原因 | 替代做法 |
| --- | --- | --- |
| `hasToolCall('ask_question')` 作停止条件 | 参数校验失败也会停，「允许修正一次」失效 | `stopWhen: [stepCountIs(3), askQuestionReady]`，检查最后一步 `toolResults` 中 `nextAction === 'await_user'` |
| `maxTokens` | v6 已更名，设置实际不生效 | `maxOutputTokens` |
| 工具只有定义、由 UI/会话层事后补 tool result | 留下未配对调用，刷新后上下文悬空 | 工具带 `execute`，在工具内返回降级结果 |
| `execute` 内等待学生作答 | 工具调用悬在内存，刷新即丢 | 立即返回 `nextAction: 'await_user'`，问题数据就绪即停 |
| 只在 UI 回调里过滤开闸标记 | 协议消息与历史仍被污染 | 适配器**两处**清理：流事件 + `response.messages` |
| `Object.values(...).join(...)` 之类通用拼接构建上下文 | 字段名/内部 ID 泄进上下文，顺序不确定 | 显式组装，用户答案用固定模板（协议第 6 节） |
| `isLoading` 之类可写布尔量表示运行状态 | 双写、迟到事件写回旧值 | 由 `turns.at(-1)?.status` 派生 |
| `useChatSession` 返回 `setState`，或把 reducer 写在组件内 | 分层没发生，只是换了个文件 | `useReducer` + 纯函数 `reduceSession` |
| 模式靠比对提示词推断 | 改提示词后模式显示失准 | 显式设置值 `teaching_mode`，随 turn 存 `modeSnapshot` |
| 提示词里出现 `〖response〗/〖question〗` 等格式规则 | 与工具协议冲突 | 提问只走 `ask_question` 工具；教学意图保留，格式规则全删 |
| 普通模式靠提示词「不要提问」 | 提示词是建议，不可靠 | `normal` 模式**不注册工具**（代码级保证） |
| 端点不支持工具时静默回退到标签解析 | 验收项无法证明，等于不实陈述 | 显示具体原因（含端点与模型名）+ 建议切到常规模式 |
| 自动重放未完成的运行、批量迁移旧历史数据 | 重复调用副模型 / 有写入风险 | `streaming` → `interrupted` 并提示；旧键只读，仅「继续对话」才写新键 |
| 假保存成功、空 catch 吞异常 | 用户以为存上了 | 保存失败返回 `{ ok:false, reason }` 并在界面提示 |
| 未经用户验收就把 HANDOFF 任务标为 ✅ | 进度失真，下一轮在错误前提上开工 | 只标 🔵 待验收 |

## 6. 关键参数（改动须先改文档并记录）

- `ask_question`：`question` 去空白后 1–500 字符；`context` 可选、≤2000 字符；`jsonSchema` + `additionalProperties: false`；**问题 ID 由程序生成**；schema 之外必须手写校验函数（长度、去空白、未知字段、模式是否允许、本轮是否已问过相同文本）。
- 拒绝也是**合法返回**：`{ status:'rejected', reason }`（`invalid_input` / `duplicate_question` / `mode_not_allowed`）。
- **一轮允许多个问题**：每个调用都执行、都返回配对结果，一个都不丢弃；每轮问几个由教学指令软引导（2–3 个），代码**不设数量硬上限**（`决策记录.md` B-3）。
- 预算：每轮最多 3 步；副模型**并发上限 4**（超出排队、失败隔离）；主运行 120s，副模型 45s 且不超过主运行剩余时间；`maxRetries: 0`（重试策略留给上层）。
- 结束原因：`completed | awaiting_user | failed | cancelled | limit_reached`，不可合并。
- 存储：新键 `chat_histories_v2`，`schemaVersion: 2`；保存时机＝用户发送、工具完成、作答提交、运行结束**四个点**。
- **禁止入库**：函数、`AbortController`、`apiKey`、`endpoint`、reasoning 原文、开闸标记。

## 7. 必须验证的命令

改动后至少运行与本任务相关的项，并保留**原始输出**（摘要写进 HANDOFF 第 2 节的证据位置）：

```bash
pnpm install --frozen-lockfile                          # 仅在 A1 执行；报错说明锁文件有问题，先解决
node --test src/agent/__tests__/ src/utils/__tests__/   # 运行层 / 纯函数测试（目录存在时）
npx vite build                                          # 构建通过
npx eslint <改动的文件>                                  # 改动文件必须干净
npx eslint .                                            # 全量对照基线：既有 15 错误 / 3 警告，不得增加
```

- 测试用 `node --test` + `ai/test` 的 `MockLanguageModelV3`，**不要自建模型 mock**（注入假的副模型 agent 对象做服务层测试是允许的）。
- 测试文件放在 `src/agent/__tests__/`、`src/utils/__tests__/`，**不得出现真实端点地址或密钥**。
- 被 Node 测试导入的模块**不得**依赖 Vite 专有能力（`?raw` 导入、`@/` 别名、JSX）；需要时把教学指令等内容作为参数注入，`?raw` 只在模式装配的入口处使用。
- 测试要断言「给定一串模拟模型输出 → 事件序列 / 状态」，而不是「某函数被调用过」。
- `node --test` 只能覆盖运行层与纯函数；**mock 不能替代真实端点验收**。
- 真实端点脚本（`scripts/*.mjs`）只从环境变量读配置（`PROBE_BASE_URL / PROBE_API_KEY / PROBE_MODEL`），输出中密钥打码。

## 8. 回答要求

- 不确定或做不到的**直接说不确定**，用「应该可以」「理论上支持」代替证据视为未完成。
- 不做总结性描述（如「测试通过」「端点支持工具」），一律给命令原文与输出。
- 发现文档与源码不一致时，以源码事实为准报告差异，不要静默按文档写。

## 9. 最容易被偷工减料的地方（自检用）

| 表现 | 怎么证明没偷工 |
| --- | --- |
| 只用 mock 验证后声称通过 | 出示真实端点的原始 `response.messages` 与步数 |
| 工具卡由 UI 事后补结果 | 指出工具定义里的执行函数；检查运行结束时的消息是否配对 |
| 用 `hasToolCall` 当停止条件 | 搜索 `hasToolCall`，结果必须为零 |
| 只在一处清开闸标记 | 适配器里应有**两处**过滤；打印 `response.messages` 验证 |
| 顺手重构旧 `ChatPage` | diff 只涉及第 3 节允许清单内的文件 |
| 抄回 `isLoading` 式双写 | 新代码中无此类可写布尔状态 |
| reasoning 被拼进上下文 | 检查上下文构建函数只取文本与协议消息 |
| 说「测试通过」但不给测试文件 | 列出测试文件名与用例名 |
| 「整体跑了一遍都正常」代替验收 | 总纲第 6 节清单**逐项**执行，记录端点、模型、日期与结果 |
| HANDOFF 没更新或只写「已完成」 | 七项清单逐项更新，证据位置可点开核对 |

## 10. 术语

- **HANDOFF**＝`docs/agent-mvp/HANDOFF.md`，跨会话的进度交接文件，是「做到哪了」的唯一依据。
- **开闸标记**＝`AgentModel.createStreamGateFetch` 注入的零宽空格（U+200B），仅用于让 provider 立刻转发流数据，**不属于任何内容**，协议消息中不允许出现。
- **规范事件**＝`run-started / text-delta / reasoning-delta / tool-started / tool-completed / tool-failed / run-finished`。
- **turn**＝一个会话中的一轮，同时保存 `modelMessages`（回传模型）与 `parts`（渲染），由会话层**统一更新**。
- **降级**＝副模型失败时问题仍可用：`optionsStatus:'unavailable'`，界面提示「候选答案生成失败，可以直接输入回答」，**不显示成空白的成功态**。

## 11. 时间与裁剪

- 估时是工作块参考，**不是承诺**。
- 时间不够时按序裁剪：工具卡细节动画 → 旧会话继续写入 v2 → 刷新恢复待答问题（降级为中断）→ 跳过问题按钮 → 英文文案。裁剪须用户同意，写入决策记录，HANDOFF 中标 ✂️。
- **不可裁剪**：真实工具调用、调用与结果配对、停止并等待用户、错误可见、旧历史可读、作答只提交一次、协议无开闸标记、无悬空 tool call。
- 核心验收未过时，`agent_runtime` 开关保持关闭（默认关），用旧版本交付。
