# Agent 改造 · 分阶段开发工作包

本目录把 `docs/AGENT_MVP_PLAN.md`（总纲）里的方案拆成可以逐个交给 AI 执行的工作包。每个阶段一个文件，包含五样东西：

1. **要解决什么问题**（问题与约束）
2. **为什么这样做**（方案比较、每个决定的理由、放弃的方案和代价）
3. **需要你决策的点**（不替你决定的事）
4. **怎么实施**（任务清单，每条含做法和判据）
5. **怎么验收和监督**（证据要求、反问清单、偷工减料的识别方法）

总纲里保留总体目标、代码事实、架构、验收清单；本目录不重复这些，只写阶段内部的细节。

## 与 AI 协作的固定循环

每个阶段重复这七步。前四步不写代码，这是关键。

| 步骤 | 你做什么 | 你要求 AI 做什么 | 产出 |
| --- | --- | --- | --- |
| 1 读 | 把 `README.md`、`01-核心协议.md`、本阶段文件、总纲第 2 节一起提供给 AI | 复述「要解决什么」和「约束是什么」，指出理解不了或与你不同的地方 | 一份复述 |
| 2 讨论 | 阅读 AI 对**决策点**的回答 | 针对本阶段每个决策点给出选项、倾向和理由，明确说哪一项它无法判断、需要你定 | 决策意见 |
| 3 决策 | 逐条拍板（可以推翻 AI 的倾向） | 把结论写进 `决策记录.md`，格式：问题 / 选项 / 结论 / 原因 / 放弃的方案 / 遗留风险 | 决策记录 |
| 4 定计划 | 确认任务顺序和本阶段不做什么 | 按任务编号排序，声明每条任务的完成判据和它**不会**碰的文件 | 任务顺序表 |
| 5 实施 | 一次只授权一个任务编号 | 完成一个任务就停下来，出示证据，等你看过再继续 | 代码 + 证据 |
| 6 验收 | 按本阶段「验收证据」逐条检查，缺证据就不通过 | 运行指定命令、贴出原始输出，不做总结性描述 | 原始输出 |
| 7 记录 | 填完成判据，更新 `决策记录.md` | 写明已知限制和下一阶段的输入，并按 `HANDOFF.md` 末尾清单更新进度 | 阶段小结 + 交接 |

**为什么把讨论和决策放在写代码之前**：这一层是协议设计（谁在说话、什么时候停、结果属于谁）。协议定错，代码写得再整齐也只能重写。讨论成本是几分钟，返工成本是几小时，而两天窗口里返工是不可承受的。

**为什么一次只授权一个任务**：任务的完成判据是独立的，批量交付会让"哪一条没做到"变得无法分辨。分开做，你随时可以停在一个可运行的状态上。

## 可复制的开工提示词

```
我在做问知轩项目的 Agent 改造，当前进行【阶段 X · 任务 X1】。

背景文件：docs/agent-mvp/HANDOFF.md（先读，确认当前进度）、
          docs/AGENT_MVP_PLAN.md（总纲）、docs/agent-mvp/01-核心协议.md、
          docs/agent-mvp/X-阶段文件.md，以及对话里的既有结论。

要求：
1. 动手前先复述你对这条任务的理解、判据、以及你不确定的地方。
2. 只做 X1，不要顺手改其他文件。确实必须改时，先列出来等我同意。
3. 不要引入新依赖，不要升级依赖，不要改旧 ChatPage 路径。
4. 完成后给出：改动文件清单、逐条判据的自检结果、可直接复制的验证命令和原始输出。
5. 不确定或做不到的，直接说不确定，不要用"应该可以"代替证据。
6. 结束前按 HANDOFF.md 末尾的清单更新进度。
```

最后两条是针对本项目的常见失败模式，见下节。

## AI 在本项目最容易偷工减料的地方

| 表现 | 为什么危险 | 怎么识破 |
| --- | --- | --- |
| 只用 mock 验证，然后说"验证通过" | 工具协议是否被真实端点支持，是本次最大的未知数，mock 测不出来 | 要求出示真实端点的原始 `response.messages` 和步数 |
| 把工具做成不带执行逻辑的定义，由 UI 事后补结果 | 运行结束时留下未配对的 tool call，刷新后上下文悬空 | 检查工具定义里有没有执行函数；检查运行结束时的消息 |
| 用 SDK 内置的 `hasToolCall` 当停止条件 | 参数校验失败也会停，"允许修正一次"直接失效 | 搜索代码里的 `hasToolCall` |
| 只在界面回调里过滤开闸标记（U+200B） | 协议消息和历史仍被污染 | 搜索适配器里对开闸标记的处理位置，要求打印 `responseMessages` |
| 顺手重构旧 `ChatPage` | 拿 18 日要投递的稳定版本去冒险 | 要求 diff 只涉及新目录；看到旧文件被改就要求解释 |
| 把 `isLoading` 这类双写状态抄进新层 | 迟到事件会把新会话的状态改回旧值 | 搜索新代码中的布尔加载状态，看它是否由运行状态派生 |
| 把 reasoning 文本拼进模型上下文 | 模型上下文里出现用户没说过的话，行为不可控 | 检查上下文构建函数是否只取文本和协议消息 |
| 说"测试通过"但不给测试文件 | 无法判断测的是实现细节还是行为 | 要求列出测试文件名和用例名，自己跑一遍 |

## 跨阶段约定

- **术语**：开闸标记＝`AgentModel` 注入的零宽空格（U+200B），仅用于让 provider 立刻转发流数据，不属于任何内容。协议消息里不允许出现它。
- **不变量**（任何阶段都不得违反，验收时逐条检查）：
  1. 每个 tool call 都有配对的 tool result；
  2. 每个事件都带 `runId`，不属于当前运行的事件被丢弃；
  3. 学生的回答是新的 user 消息，不是工具结果；
  4. 工具执行完不等于学生回答完；
  5. 依赖以 `pnpm-lock.yaml` 为准。
- **改动边界**：新增文件在 `src/agent/`、`src/hooks/useChatSession.js`、`src/pages/AgentChatPage/`、`src/components/{MessageContent,ToolCallCard}/`、`src/utils/{conversationState,historyStore}.js`、`scripts/` 内。旧 `ChatPage`、`StreamingParser`、`AgentModel` 在本期只允许被读取和复用，不允许被改写——除非在决策记录里明确同意。
- **时间不是承诺**：估时是工作块参考。核心验收未过时，`agent_runtime` 开关保持关闭，用旧版本投递。
