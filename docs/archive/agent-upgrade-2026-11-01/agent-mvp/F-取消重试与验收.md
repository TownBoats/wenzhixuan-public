# 阶段 F · 取消、重试与验收

估时 2 小时｜任务 F1–F4｜依赖 E 完成｜产出：失败路径可用、逐项验收记录、18 日投递版本的决定

## 1. 要解决什么

补齐"出错时会发生什么"，并把前面五个阶段的结论落到可检查的证据上：

1. **取消**：现有产品完全没有取消能力。`AgentModel` 的超时控制器在函数内部创建，外部拿不到；用户离开页面或切换会话时，旧请求仍在写入界面。
2. **重试**：现有实现是"整轮重试"——`AgentModel` 内部 3 次 + SDK 默认 2 次。在有工具执行的流程里，重放意味着重复的副模型调用、重复的卡片、重复的协议消息。
3. **错误可见**：端点不支持工具、副模型失败、保存失败，都要有可读的落点，不能静默退回旧路径并声称"Agent 在运行"。
4. **验收**：把总纲第 6 节的清单逐项跑完，并决定 18 日投递哪个版本。

## 2. 为什么这样做

### 2.1 为什么重试只允许最后一轮

| | 只重试最后一轮（推荐） | 任意轮重试 + 截断后续 |
| --- | --- | --- |
| 实现 | 丢弃该 turn 的协议消息与问题记录，以新 `runId` 重跑 | 需要找到目标 turn，截断它之后的所有 turn，处理其中的问题状态、工具卡片、待答状态 |
| 风险 | 几乎没有残留态 | 截断不干净时会留下悬空调用或重复卡片 |
| 用户体验 | 与现有"重试上一条"接近 | 可以从中间某轮重来 |

**为什么接受这个限制**：本次改造的核心风险在协议正确性上，不在重试的灵活度上。两天窗口里，把重试做成"只作用于最后一轮"能保证不留残留态；"从中间重来"是产品增强，记入后续事项。

**关键约束**：重试必须产生新的 `runId`，并取消原运行。如果实现成"在原工具结果后面再追加一次相同调用"，协议里就会出现两个 `ask_question` 结果，下一轮模型会困惑。

### 2.2 为什么取消要覆盖主副两个请求

取消只传给主模型时，副模型可能仍在跑并稍后写回，把已经取消的那张工具卡改成"完成"。这类 bug 在界面上表现为"点了取消，几秒后卡片自己完成了"，很难查。所以 `AbortSignal` 必须同时传给主模型和副模型（B1、B3 都已预留），并且迟到结果由 `runId` 守卫丢弃（C1）。

**为什么"取消"和"超时"要区分**：超时是失败，应该可以重试并给出失败提示；取消是用户意图，不该显示为错误。`01-核心协议.md` 的结束原因里两者分别是 `failed` 和 `cancelled`。

### 2.3 为什么端点不支持工具时不能静默回退

技术上可以做到：检测到工具调用失败，就退回旧标签解析，用户看到的是一次正常回答。但这样一来：
- 用户以为自己用的是工具驱动的 Agent，实际上不是；
- 验收清单里"真实工具调用"这一项无法证明；
- 简历表述会变成不实陈述。

所以处理方式是显示具体原因（含端点和模型名，方便排查），并说明程序已降级到**无工具兜底模式**（该模式不注册工具，本就是这类端点的正确用法；用户不可手动切换，见 `决策记录.md` B-1）。

### 2.4 为什么验收必须记录端点和日期

总纲 11 节写明测试不能替代真实端点验收。代码会变、端点行为会变、免费额度会变。一条"验收通过"的记录如果没有端点和日期，几周后无法判断它是否还成立。这也是简历表述的依据：没有证据的能力不写。

## 3. 需要你决策的点

### 决策 1：18 日投递哪个版本

这是本阶段唯一的重大决策，且要基于 F4 的实际结果：

| 情况 | 建议 |
| --- | --- |
| 核心验收全过 | `agent_runtime` 默认改为开，用新路径投递 |
| 核心验收大部分过，个别次要项未过 | 保持默认关，演示时手动打开；简历只写已通过的能力 |
| 核心验收未过 | 默认关，用旧版本投递；新路径留在开发分支，简历不写未完成的能力 |

**哪些算"核心"**：真实工具调用、调用与结果配对、停止并等待用户、错误可见、旧历史可读、作答只提交一次、协议无开闸标记、无悬空调用。

**为什么要把这个决策留到这里**：现在无法预知端点表现。提前承诺"一定用新版本投递"，会让人在压力下把未验证的能力写成已完成。

### 决策 2：`agent_runtime` 开关的去留

验收后有三种做法：

- A. 默认开，并在下一个版本删除旧路径（倾向）
- B. 默认开，长期保留开关
- C. 一直默认关，手动开启

**倾向 A**，但要排在投递之后执行。理由：两套路径长期并存会让后续每次改动都要考虑两边（C 阶段已经指出这个成本）。删除旧路径属于清理工作，不占用本次窗口。

### 决策 3：取消按钮的交互位置

现状没有取消。需要确认：放在发送按钮位置（发送后变成取消）、还是消息区（运行中的气泡上）？倾向"发送按钮位置"，因为用户的心智是"停下手上的事"，而且不需要滚动到消息区。

## 4. 任务清单

### F1 · 取消

**做法**：运行中的界面显示取消入口；点击后中止当前运行的控制器；运行层收到中止后停止产生事件；结束原因为 `cancelled`；已收到的内容保留。

**为什么保留已收到的内容**：清空会让用户以为内容丢了，也可能触发一次多余的重试。

**判据**
- 取消后界面停止更新；
- 若运行层在被取消后仍吐出一个事件（模拟），该事件不改变状态；
- 副模型请求也被中止（可用日志或请求计数验证）；
- 取消不产生错误提示。

### F2 · 重试最后一轮

**做法**：丢弃最后一轮的协议消息与问题记录，以新 `runId` 重跑该轮的用户消息；界面显示"重新生成中"，保留原内容直到新内容到达。

**为什么显示"重新生成中"而不是清空**：避免用户误以为内容丢失；也便于你观察重试前后是否出现重复卡片。

**为什么不沿用旧的整轮重试**：见 2.1。

**判据**
- 重试后无重复工具卡、无重复工具消息、无旧流污染；
- 重试中如果用户点了取消，状态回到可输入；
- 连续点重试只产生一次运行。

### F3 · 错误映射

**做法**：把运行层的错误分类成可读文案。

| 情况 | 界面 |
| --- | --- |
| 端点不支持工具调用 | "当前模型不支持工具调用"，附端点与模型名，并说明已降级到无工具兜底模式 |
| 副模型失败 | 问题卡仍在，显示"候选答案生成失败，可以直接输入回答" |
| 保存失败 | "对话未能保存到本地"，附可执行动作（清理旧会话） |
| 超时 | "请求超时"，无自动重试提示 |
| 取消 | 不显示为错误 |

**为什么错误里可以出现端点与模型名**：它们不是密钥，且是排查必需的信息。密钥、完整请求头、用户配置不能出现。

**判据**：五种情况各有可读文案；错误信息中不含 `apiKey`；不出现静默回退到标签解析的行为。

### F4 · 逐项验收

**做法**：打开总纲第 6 节清单，逐条执行并记录端点、模型、日期、结果。人工部分用闭包这一主题走正常链路和失败链路。

**为什么用同一个主题贯穿**：A 阶段基线、B7 单跑、D8 界面、F4 验收都用闭包，出现差异时能快速定位在哪一层引入。

**为什么清单里有些项必须人工**：工具卡的四态、窄屏可读性、文案是否可读、折叠是否可键盘操作，这些没有自动化手段能替代。

**判据**：清单有逐项结果；未通过项写明现象与原因；`决策记录.md` 有 F 阶段记录。

## 5. 验收证据

1. 取消的现场记录（含副模型是否被中止的证据）。
2. 重试前后的协议消息对比（无重复）。
3. 五种错误的界面表现（截图或文案摘录）。
4. 总纲第 6 节清单的逐项结果，含端点、模型、日期。
5. `决策记录.md` 的 F 阶段条目与投递版本决定。
6. `pnpm build` 通过的输出；改动文件的 lint 结果。

## 6. 监督与反问

- "取消之后，副模型还在跑吗？"——需要实际证据（请求日志或计数），不接受代码层面的"应该会中止"。
- "重试后的协议消息里，`ask_question` 出现了几次？"——必须是一次。这是重试最容易出错的地方。
- "如果端点不支持工具，界面上看到的是什么？会不会静默退回旧路径？"——要求实际操作一次（可用一个不支持工具的模型名触发）。
- "验收清单第 9 条（取消/切换/重试后迟到流不污染）你是怎么证明的？"——需要构造迟到的场景，而不是只跑一遍正常流程。
- "简历里你打算写哪几句？"——逐句对照本次通过的能力，未通过的不写。

**识别偷工减料**：如果验收清单被"整体跑了一遍，都正常"这样的描述代替，等于没验收——那份清单的每一项都需要独立的证据。如果错误映射只有一句通用的"请求失败"，F3 没有落地。

## 7. 遗留风险

- 跨刷新的"外部服务恰好执行一次"不在本期保证范围内（计划里已声明）。
- 取消的及时性取决于端点是否响应中止，浏览器端只能发信号。
- 免费额度端点在演示时可能限流，表现为 `failed`，需要在演示前确认额度。
- 如果 F4 有未通过项，需要在 18 日投递前把 `agent_runtime` 恢复为默认关并重新构建。
