# 阶段 E · 历史存储与刷新恢复

估时 2 小时｜任务 E1–E4｜依赖 C2（保存接入）、D 可用后｜产出：新会话可保存恢复（含待答问题），旧历史可读且不被改写

## 1. 要解决什么

三件事，其中一件是新能力：

1. **待答问题不持久化（新能力）**：`useQuestionFlow` 的问题列表只存在内存 reducer 里，刷新即失去。本次要求"刷新后待答问题恢复为可回答"——这是**新增**，不是保留现有行为。方案第一版把它写成"保留"，是错的，这里更正。
2. **存储无异常处理**：`useChatHistory` 的 `JSON.parse` 与 `localStorage.setItem` 都没有 try/catch。数据一旦损坏，初始化时抛错，页面白屏，且用户没有任何办法自救。
3. **新旧格式共存**：新记录带工具调用和问题状态，旧记录只有文本和 `answer-card`。两者要能同时显示，且旧记录不能被改写。

## 2. 为什么这样做

### 2.1 为什么分键存储，而不是在同一数组里加版本号

localStorage 的写入是**整键覆盖**。混存方案每次保存都要：读全量 → 找到这一条 → 改 → 序列化全部 → 写回。这个过程中：

- 任何一次异常（配额满、序列化失败）都可能把整个数组写坏；
- 并发写入（两个标签页）会互相覆盖；
- 首次写入前需要备份快照，备份本身也要占配额，而配额满正是最需要备份的时候。

分键之后，旧键在本次改造中**只读**，新会话写新键。写入面天然隔离，"写坏用户数据"这类事故不可能发生。

**代价要认**：删除和重命名要作用于两个键，且同一个会话如果既在旧键又在新键（用户继续了旧会话），需要按 ID 去重并让新键优先。这是明确的、可测试的逻辑，比"整数组重写可能损坏"容易处理。

### 2.2 为什么 v1 适配在内存里做，不批量迁移

批量迁移需要：解析全部旧记录 → 转成新格式 → 写回 → 失败回滚。三天内做完并在真实用户数据上验证，成本高，且一旦出错影响的是用户已有的全部历史。

内存适配的做法是：读到旧记录时，现场投影成 turn 结构用于显示，**不写回**。用户继续对话时，该会话以同一 ID 写入新键，此时旧键里的同名记录在列表中被隐藏（新键优先）。旧数据始终是原样。

**为什么"继续对话才迁移，而不是打开就迁移"**：迁移即写入，写入就有风险。只迁移用户真正在用的会话，风险面与工作量都最小。

### 2.3 为什么保存时机是那四个点

用户发送、工具完成、作答提交、运行结束。这四个点都是**状态转换的边界**，转储的数据是稳定的。

**为什么不每个 token 保存**：正文增量不进入 `messages`（现状即如此，所以流式过程本来就不落盘），如果为了"实时感"而每个 delta 都写一次全量历史，代价随对话长度线性增长，配额很快撑不住。

**为什么不只在运行结束保存**：运行结束前刷新会丢掉整轮内容。工具完成时落盘，能保证"提问已经产生"这件事不会因为刷新而消失。

### 2.4 为什么刷新后不自动重放

刷新时可能有一个处于 `streaming` 的 turn。如果自动重放，会：
- 重复调用副模型（额度消耗）；
- 产生与刷新前的部分内容拼接的奇怪结果；
- 如果这轮已经调用过工具，重放等于重复执行。

所以标记为 `interrupted`，保留已有内容，提示用户"这一轮没有完成"。这**不等于**后台任务恢复或断点续传——内存里的计时器和控制器无法恢复，这一点要写清楚，避免被当成能力声明。

## 3. 需要你决策的点

### 决策 1：历史列表怎么展示新旧两类会话

| 选项 | 说明 |
| --- | --- |
| A. 合并成一个列表，新键优先（倾向） | 用户看到连续的会话历史，不感知存储结构 |
| B. 分组显示（"新" / "旧"） | 结构清楚，但会暴露实现细节 |
| C. 只显示新键，旧键通过"导入"按钮访问 | 界面最干净，但用户会觉得历史丢了 |

**倾向 A**。理由：存储分键是**实现手段**，不该泄漏到界面上。用户关心的是"我之前的对话还在不在"。

### 决策 2：配额满时怎么处理

localStorage 通常 5MB 左右。本轮改造后每条记录都会变大（要存协议消息），所以配额问题会比现在更早出现。

| 选项 | 说明 |
| --- | --- |
| A. 提示保存失败，本次对话只保留在内存，并建议删除旧会话（倾向） | 用户知道发生了什么，可以自救 |
| B. 自动删除最旧的会话腾出空间 | 静默删数据，风险大，不做 |
| C. 超出后只保存最近 N 条 | 需要定义 N，且用户不知道被丢了多少 |

**倾向 A**，并在提示中给出可执行的动作（打开历史列表删除旧会话）。**为什么不做 B**：用户的数据比自己的一次保存失败重要。

### 决策 3：旧会话继续对话后的保存策略

需要你确认是否采纳"继续即写入新键，旧键对被隐藏"。这是 2.2 的核心。

- 采纳（倾向）：一次写入风险，之后都走新路径。
- 不采纳：旧会话只读，用户想继续只能在相同上下文里新开会话。体验差，但绝对不写旧数据。

## 4. 任务清单

### E1 · `src/utils/historyStore.js`

**做法**：封装 v2 读写，对上层返回结果而不是抛异常。

| 函数 | 行为 |
| --- | --- |
| `loadAll()` | 读新旧两个键；旧键解析失败时跳过坏条目并返回"有损坏"标志，不抛错 |
| `loadById(id)` | 新键优先，找不到再查旧键（返回投影后的只读结构） |
| `saveConversation(conv)` | 写新键；捕获配额异常，返回 `{ ok:false, reason:'quota' }` |
| `deleteConversation(id)` | 同时作用于两个键 |
| `renameConversation(id, title)` | 同上 |
| `listForSidebar()` | 合并两键，按时间排序，同 ID 新键优先 |

**为什么用"返回结果"而不是抛异常**：保存失败是预期内的分支（配额满），不是异常。用返回值表达，调用方必须处理；用异常表达，很容易被一个空的 catch 吞掉，变成"假成功"——方案明确禁止显示假的保存成功。

**判据**
- 损坏的 JSON 不导致白屏，坏条目被跳过并能提示；
- 模拟配额满（可临时把待存数据撑大）时返回 `{ ok:false }`，界面有提示；
- 同一 ID 同时存在于两键时，`loadById` 返回新键内容，列表里不出现两条。

### E2 · v1 只读适配

**做法**：把旧记录的 `messages` + `uiMessages` 投影成 turns（文本片段、`answer-card` 片段），上下文构建只取纯文本。

**为什么要写适配而不是丢弃旧记录**：验收清单明确要求"旧历史正常显示"。而且旧记录里可能有用户真正需要的内容。

**为什么上下文只取纯文本**：旧记录里的两套数组已经分叉（摘要进了 `messages` 没进 `uiMessages`，`answer-card` 进了 `uiMessages` 没进 `messages`）。从分叉的数据里还原"当时到底说了什么"没有唯一答案，取纯文本是唯一稳妥的选择。

**判据**：旧会话正常显示；旧记录里的一轮多问题卡片可读；旧键内容在继续对话前后字节不变（用 `localStorage.getItem` 对比）。

### E3 · 恢复语义

**做法**：会话载入时按 turn 状态处理。

| 载入时状态 | 处理 |
| --- | --- |
| `streaming` | 标记 `interrupted`，保留已收到的片段，提示"这一轮没有完成" |
| `awaiting_user` | 恢复为可作答（问题卡、五档、输入框都可用） |
| `completed` / `failed` / `cancelled` | 原样显示 |

**为什么 `interrupted` 不自动继续**：见 2.4。

**为什么悬空调用不进入上下文**：如果刷新正好发生在模型请求了工具、工具还没返回时，协议消息里会有"只有调用没有结果"的片段。这类上下文部分端点会直接拒绝请求。所以构建上下文时过滤掉，但**保留在 parts 里用于展示和诊断**——用户能看到"这里有个没完成的调用"，我们也能据此判断问题。

**判据**：三种状态各手动验证一次（可在保存后手动改 localStorage 模拟）。

### E4 · 测试

**判据**：损坏 JSON、配额满、同 ID 合并、删除两端、旧键字节不变，各有用例，输出可贴。

## 6. 监督与反问

- "旧记录的字节数在继续对话前后变了吗？"——要求给出前后对比，不接受"没有修改旧数据"的声明。
- "配额满的时候，界面上出现的是什么？"——要求截图，不接受"会提示"。
- "刷新时正好有一个未完成的工具调用，它的调用片段去哪了？"——答案必须是"留在展示里、不进上下文"，两者都要有证据。
- "删除一个同时存在于两键的会话，新键和旧键都删了吗？"——现场操作一次，然后读两个键确认。
- "适配后的旧会话，第一轮内容显示正常吗？"——要求实际打开一个旧会话。

**识别偷工减料**：如果实现方式是"把旧记录读出来转成新格式后写回新键，然后删掉旧记录"，那这是批量迁移，不是只读适配，与本阶段的决策相反，要退回。如果 `localStorage.setItem` 外面只有一句 `console.error`，那"保存失败提示"没有落地。

## 7. 遗留风险

- localStorage 总容量在记录变大后可能更早触顶，长期需要换存储方案（不在本期）。
- 旧记录里的一轮多问题在界面上如何排列，取决于适配的投影规则，需要实际检查可读性。
- 如果用户在多标签页同时使用，两个键各自覆盖仍可能互相影响；本期不解决多标签页并发。
