# 决策记录

追加式台账。每做一个决定就写一条，不覆盖历史。格式固定，便于日后复盘和写简历时对照证据。

```text
### <阶段>-<序号> <一句话标题>
日期：
问题：（要定的到底是什么）
选项：（列出候选，含被否的）
结论：
原因：
放弃的方案与理由：
验证证据：（命令 + 原始输出要点）
遗留风险：
```

**为什么必须有这个文件**：本次改造要在两天内替换一条正在使用的对话链路，过程中会有大量"为什么不是另一种做法"的判断。不记下来，两天后只能凭记忆复盘；面试或复盘时也无法说明取舍的依据。另外，简历表述要求"只写已验证的能力"，这个文件就是验证证据的索引。

日期：2026-10-16

原因：用户已有该端点的可用配置；模型自带思考模式，用例③可在同一模型上验证 reasoning 与工具并存的风险，不必再找第二个模型。

### A-5 A3 探针结论：端点支持工具闭环；`parallelToolCalls` 不生效，去重必须由应用层做

日期：2026-10-16
问题：`https://api.deepseek.com/v1` + `deepseek-flash` 是否支持「模型调用工具 → 工具结果回传 → 继续生成」的多步闭环；一次问答中端点会不会自动串行化工具调用。
选项：（决策 2）① 端点支持工具闭环，按原方案继续；② 换端点；③ 换模型；④ 退到「模型输出结构化 JSON、程序解析后执行」的降级方案。
结论：①。端点支持工具闭环，**不启用降级方案**。另外：`parallelToolCalls: false` 被端点接受但**不生效**，一次提问仍会返回多个工具调用 → **应用层的去重（同一 `toolCallId` 只执行一次、每轮只取第一个问题）是唯一防线，不是锦上添花**。
原因：探针 ② 用 `generateText` + `stopWhen: stepCountIs(2)` 拿到 2 步、第二步产出新文本，证明多步闭环成立；⑤b 与 ⑤c 分别在「不传」与「传 `parallelToolCalls:false`」两种情况下用「一次问杭州和上海」的提示，**两者的第二步请求都带两个 `tool` 消息**（`roles=user,assistant,tool,tool`），说明该选项没有阻止并行调用。旧路径一次问答出现 3 张问题卡（见 `A-基线存档.md` 第 3 节）与这条互为印证。
放弃的方案与理由：②③ 无必要（当前端点已满足核心假设）；④ 会用掉这次改造最重要的价值——把「标签解析 + 页面触发」换成真实工具协议。
验证证据：`scripts/probe-tools.output.json`（两轮：`when=2026-10-16T11:32:27Z`、`11:35:12Z`）。要点：① status 200、1 步、工具名 `get_weather`、参数类型 `object`、`{location:"杭州",date:"2026-10-17"}`；② 步数 2、第二步文本 29 字；⑤b/⑤c 第二步 `roles=user,assistant,tool,tool`；④ `文本含零宽空格=false`、`协议消息含零宽空格=false`。原始命令：`node scripts/probe-tools.mjs`。

### A-6 思考模式与工具可以共存：不需要回传 `reasoning_content`，协议不变量 3 保持不变

日期：2026-10-16
问题：（决策 4）DeepSeek 文档写明「请求携带 `tools` 时，历史轮次的 `reasoning_content` 必须回传，否则 400」，这与协议不变量 3「reasoning 不进入模型上下文」及存储规则「禁止 reasoning 原文入库」冲突，B 阶段是否必须二选一（关闭思考模式 / 回传并放宽协议）。
选项：① 运行层关闭思考模式（`thinking.type="disabled"`）；② 把 reasoning 回传进上下文并修改 `01-核心协议.md` 的不变量 3 与存储规则；③ 换 provider 实现；④ 两样都保留，按实测行为走。
结论：④。实测在该端点该模型上**不触发该规则**：不回传 `reasoning_content` 的同轮多步（③a）与跨轮（⑥a）都是 200，且 AI SDK 组装的 assistant 消息里 `原生assistant含reasoning=0`，即 reasoning 确实没有进入上下文。因此**不变量 3 与存储规则无需修改，思考能力也保留**。强度可调：`low/medium/high/xhigh` 走 `providerOptions.openai.reasoningEffort`；`max`（文档还提到 `ultra`）不在 AI SDK 允许值内，**只能由运行层注入请求体**。

### B-3 一轮允许多个问题：代码不设数量硬上限，副模型并发 4

结论：

6. 作答节奏：**全部问题答完或被显式跳过之后**才发起下一轮；未作答的问句在上下文里写成"跳过"记录，不留缺口。

### B-10 副模型服务用 `modelAdapter` 跑；候选答案放宽为「有几档显示几档」

日期：2026-10-17
问题：（B3 开工说明的 6 个决策点）① 协议要求副模型 45 秒且不超过主运行剩余时间、且可取消，但 `AgentModel` 没有 `abortSignal`、没有 `abort()`，内部 60 秒超时的 abort 还会被它自己的 3 次整轮重试当普通错误重试；② 原判据要求「五档齐全」，缺档即整轮不可用；③ 未配置副模型由谁判定；④ `language` 参数怎么处理；⑤ B3 是否自带测试；⑥ 失败时向返回结构里放什么。另有一个前置问题：`ContentParser` 在新实现里还要不要。
选项：
- **超时与取消**：A 用 B1 的 `modelAdapter` 跑副模型（**用户选择**）／B 仍用 `AgentModel` + `Promise.race` 限时（后台请求继续跑）／C 把 `AgentModel` 的流式逻辑复制进服务。
- **档位齐全度**：A 必须五档齐全（原判据）／**B 有多少档返回多少档，≥1 条即成功，同档只留第一条（用户选择）**／C 缺档用空串补齐五项。
- **未配置判定**：**A 服务内纯函数 `isOptionConfigReady`（用户选择）**／B 由上层传 `configured` 布尔。
- **`language`**：**A 保留签名、本期不使用（用户选择）**／B 本期拼进 system。
- **测试**：**A B3 自带（用户选择）**／B 并入 B6。
- **失败细节**：**A 只返回白名单 `detail`（用户选择）**／B 返回原始错误对象（会带 `responseHeaders` / `responseBody` / `actualUrl`）。
- **`ContentParser`**：**A 复用（用户选择）**／B 服务内自写约 20 行解析／C 副模型改结构化输出。
结论：
1. **B3 用 `modelAdapter` 跑副模型**：`timeoutMs = min(45s, 主运行剩余时间)`、外部 `AbortSignal` 透传、`maxRetries: 0`、无打字机延迟。`AgentModel` 保持原样不动（旧路径仍用它）。
2. **候选答案放宽**：≥1 条可识别档位即 `status:'ready'`；每条固定 `{ level, text }`，`level` 必须是五档之一，标签外正文与未知标签丢弃；**同一档出现多次只保留第一条**；输出顺序固定 `none → heard → basic → familiar → expert`；**零条**才是 `unavailable` + `option_model_failed` + `detail:'invalid_output'`。协议 §2.2 / §2.3 已按此修改。
3. **未配置副模型由服务判定**：`isOptionConfigReady({ endpoint, apiKey, model })`（三项齐全且 endpoint 是绝对 http(s) URL），不 ready 立即返回 `option_model_not_configured` 且**零请求**；配置与 system prompt 由上层传入（运行层不读 localStorage）。
4. **`language` 保留签名、本期不使用**（B-1 结论 6）。
5. **B3 自带 11 条测试**（`src/agent/__tests__/generateAnswerOptions.test.js`），用假 fetch 的 SSE，不联网。
6. **失败只返回白名单**：`detail ∈ { timeout, cancelled, request_failed, invalid_output, 'HTTP <三位数>' }`，不含端点、密钥、请求头、响应体。
7. **复用 `ContentParser`**（`tags` 是构造参数、无浏览器依赖）；**不复用** `StreamingParser`（增量状态机）与 `useQuestionFlow`（React hook，且把解析出的数组直接当字符串用）。
原因：45 秒、可取消、不重试这三条是协议对副模型的硬约束，`AgentModel` 的结构决定了它做不到（超时 abort 被重试吞掉，外部拿不到 controller）；`modelAdapter` 已在 B1 验收，直接复用比"限时后丢弃后台请求"更诚实——后者会把额度浪费在没人等的结果上。档位放宽的理由是：五档是学生的自评梯度，不是答案的完整性要求；缺一两档时学生仍可手输或跳过，把缺档判成整轮不可用等于让一次轻微的模型偏差清空全部候选答案（界面只剩输入框）。同档只留第一条是为了避免同一屏出现两个「基本了解」。失败只回白名单，是因为 `AgentModel` / AI SDK 的错误对象会把 `responseHeaders`、`responseBody`、`actualUrl` 一并带出，而工具结果会进入模型上下文与存储。
放弃的方案与理由：B（`Promise.race`）会把"取消"变成假动作，且失败隔离与预算失真；C 是复制旧实现，两份流式逻辑必然漂移；A（必须五档）见上；C（空串补齐）会让界面出现无法作答的空档位；B（上层传 `configured`）会把判定逻辑复制到每个调用方；B（原始错误）违反"错误里没有密钥或请求头"的判据；B（自写解析）与已有实现双份维护且容易行为漂移。
验证证据：（1）`node --test "src/agent/__tests__/*.test.js"` → **20 tests / 20 pass / 0 fail**（B2 的 9 条 + B3 的 11 条）；（2）B3 用例覆盖：五档齐全 5 条且顺序固定、三档返回 3 条、同档两条取首条、零档 `invalid_output`、HTTP 500 → `detail:'HTTP 500'` 且序列化结果里不含 `example.invalid` / 密钥 / `x-trace` 头、超时 → `detail:'timeout'`、未配置 → `not_configured` 且 fetch 调用 0 次、开闸标记不进候选答案、契约错误抛错；（3）临时探针确认失败路径 **`calls = 1`**（`maxRetries: 0` 生效）且 `detail` 实测为 `HTTP 500`；（4）`npx eslint src/agent/` 无输出；全量 `npx eslint .` → 75 文件 / 9 个有问题 / **15 错误 / 3 警告**（与 A-2 基线一致）；（5）新增两个文件 `U+200B=false`、`U+3016=false`。
遗留风险：（1）失败时 AI SDK 仍会把完整 `APICallError`（含 `url`、`requestBodyValues`）打印到 **stderr**，虽然不在我们的返回结构里，但 D/F 阶段若把 stderr 收进日志或上报，会泄露端点——接日志时必须只取我们的 `detail`；（2）`HTTP <码>` 本身是一种侧信道（暴露状态码），按白名单已接受；（3）副模型请求同样经过开闸 fetch，会多一条空 SSE（用户已确认可接受），换端点后需复验；（4）副模型提示词的三层覆盖仍在配置层，B4/D 阶段由上层读取后传入，E 阶段迁移旧配置时要保证提示词来源不变；（5）档位放宽后界面必须按 `options.length` 渲染（D4 判据已补），F4 验收要确认缺档时没有空行。

### B-11 `ask_question` 的校验顺序、状态归属与异常语义

日期：2026-10-17
问题：（B4 开工说明的 8 个决策点）① `toolCallId` 去重与参数校验谁先；② 两张"记忆表"放哪、活多久；③ B4 测试注入哪一层；④ "未配置副模型"在 B4 是否再判一次；⑤ `questionId` 形式；⑥ 工具结果是否携带 `options`；⑦ `execute` 内部异常的语义；⑧ 工具 description 文案。
选项：
- **校验顺序**：**A `toolCallId` 去重放最前（用户选择）**／B 保持协议原顺序（模式→字段→文本重复→去重）／C 在文本重复前插入一次去重查询。
- **状态归属**：**A 工具闭包内、每轮一个实例（用户选择）**／B 由 B5 传入外部 store。
- **测试注入**：**A 注入 `generateOptions` 假函数（用户选择）**／B 注入 `baseFetch` 走假 SSE。
- **未配置判定**：**A B4 先调 `isOptionConfigReady`，不 ready 零请求（用户选择）**／B 只依赖 B3 的返回值。
- **`questionId`**：**A `q_` + 12 位十六进制（用户选择）**／B `q_` + 进程内自增。
- **工具结果**：**A 携带完整 `options`（用户选择）**／B 精简为状态字段。
- **异常语义**：**A `rejected('internal_error')` + 固定文案（用户选择）**／B 伪装成 `option_model_failed` 降级／C 不 catch，让 SDK 生成 `tool-error`。
- **description**：用户确认草案「向学生提出一个需要他作答的问题。需要同时了解几个方面时，可以在一轮里调用多次；不要在正文里写问题。」
结论：
1. **`toolCallId` 去重排在最前**，命中即返回上次结果、不再校验。协议 §2.2 已按此改顺序，并补理由段。
2. **两张记忆表放工具闭包**：`resultsByCallId`（幂等）与 `askedTexts`（本轮文本去重）。工具实例由 B5 每轮创建一次，轮结束销毁；不放模块级全局表（跨轮误杀 + 泄漏）。
3. **测试注入 `generateOptions`**，B4 只测自己的校验、去重、编排；B3 的解析行为由 B3 自己的 11 条测试覆盖。
4. **B4 先判 `isOptionConfigReady`**：不 ready 直接返回 `ready + unavailable + option_model_not_configured` 且**不调用** `generateOptions`，使"零请求"在 B4 这一层可断言。
5. **`questionId` 用 `q_` + 12 位十六进制**（`crypto.randomUUID` 去横线截断，无 crypto 时回退时间戳+序号）。
6. **工具结果携带完整 `options`**（协议 §2.3），模型据此知道提供了哪些选项。
7. **异常 → `rejected('internal_error')`**，`message` 固定为一句可执行的提示，**不含异常原文**；协议 §2.2/§2.3 已补该枚举与理由。
8. description 用草案原文；参数规则仍只在 `jsonSchema` 与 description 里，不复制进教学提示词。
原因：去重若排在文本校验之后，重放会先命中"本轮已问过这段文本"被判 `duplicate_question`，永远拿不到"上次结果"，不变量 5 失效——这是开工时发现的协议顺序缺陷，不是风格选择。记忆表只能活一轮：跨轮重复提问是合法的（学生要求"再讲讲"时模型应当能再问），全局表会误杀。异常如实标注为程序错误，是为了不让程序 bug 伪装成"副模型失败"而误导排查；同时不能把异常原文回给模型（可能含端点、请求头）。

### B-12 B5 的运行边界：并发信号量在装配层、身份必传、`limit_reached` 以 `finishReason` 判定、单次运行不重试

日期：2026-10-17

结论：
1. **并发上限 4 由 B5 在装配层实现**：B5 构造 `ask_question` 时把 B4 的工具对象包一层（对象展开保留 `description` / `inputSchema`，只覆写 `execute`），信号量是本轮私有的（随 B5 调用创建、随轮销毁），峰值可在包装层计数供 B6 断言。**B4 一行不改**。

4. **B5 是单次运行**：一次调用恰好发一次 `run-started` 与一次 `run-finished`（含取消 / 超时 / 失败路径，用 `try/finally` 保证）；内部不重试，重试由上层换新 `runId` 再调一次（F2）。
5. **`endedBy` 一对一映射**：`finished` → 结论 3 的三选一；`cancelled` → `cancelled`；`timeout` → `failed`；`failed` → `failed`。`timeout` / `failed` 的 `run-finished` 带空 `responseMessages`（B1 在这三类路径上都返回空数组，`modelAdapter.js:346-390`），因此这两类路径的正文不进上下文，也不会留下悬空调用（不变量 1）。
原因：并发上限属于「本轮预算」，只有装配层知道本轮边界；放在 B3 会变成跨轮累积的全局状态，取消时槽位可能泄漏，等于把预算语义落错层。身份必须由上层持有：`runId` 是「丢弃不属于当前运行的事件」的比较基准（不变量 6），若运行层能自造，会话层就要从 `run-started` 事件里回读 runId 再比较，多一个会漂移的真相源；而规则 §3 本就把身份分配划给会话层，B7 脚本多写三行即可。`limit_reached` 用 `finishReason` 而非步数判定，是因为 `tool-calls` 恰好表达「最后一步以工具调用收尾、工作被上限截断」，而 `stop` 表达「模型自己收住了」——按步数判会把「第 3 步自然说完」误报成达到上限，界面提示与实际不符（B6 的「超步数 / 提问后停止」两个用例方向也会互相矛盾）。`timeout` 不并入 `cancelled`，是因为超时不是用户取消，D/F 的文案与 F2 的重试判断都依赖这个区分。
放弃的方案与理由：B（改 B4）会把已验收、已有 15 条测试的工具拖回返工，而包装层能零侵入做到同一件事；C（B3 模块级信号量）是跨轮全局状态，与「每轮一个工具实例、记忆表随轮销毁」（B-11）的设计直接冲突。B/C（身份缺省）见上，且 C 会让「一次运行的身份」出现两个来源。B（按步数判 `limit_reached`）与 C（无 `await_user` 即 `completed`）见上。B（`timeout → cancelled`）会让界面在超时后显示「已取消」，F2 也可能据此误判为「用户主动放弃」而不再提供重试。C（内部安全重试）会让一次调用出现多个 `run-started`，稀释「`run-started` 固定本轮配置」的语义，并把重试策略从 F2 提前散落到运行层；`maxRetries: 0`（B1）已经表明本层不做重试。
验证证据：用户 2026-10-17 逐条选择 A（5 项全部）。本条为开工前置决策，**尚无运行证据**；实施后用 B6 的 6 个用例（尤其「提问后停止」「超步数」「取消」）验证结论 3、4、5。
遗留风险：（1）`finishReason` 的取值依赖 SDK 归一化结果，若某端点在「模型想继续调工具」时给出别的值（例如 `other`），会被判成 `completed`——B7 真实端点跑通后需复核一次 `finishReason` 实测值；（2）包装层覆写 `execute` 时若漏掉 `inputSchema` 的透传，SDK 会在进入 `execute` 前失去参数校验，表现为「未知字段不再被拦」，B6 需断言包装后工具仍带 `inputSchema`；（3）信号量排队期间被取消的处理（不进入 `execute`、返回 `rejected('internal_error')`）是 B5 的实现细节，未在协议中定义新的 reason，F3 做错误映射时不要把它当成程序 bug 上报；（4）「单次运行」意味着运行层不做任何自动重放，F2 的重试必须在会话层用新 `runId` 发起。

### C-1 会话层四个前置决策：自动续轮、跳过语义、重试语义、待答状态用数组

日期：2026-10-17
问题：（`C-开发指导.md` 开工前准备第 1 节）C1/C2 的 state 形状与命令语义有四处必须先定，否则状态机写出来就要返工：① 作答后是否自动开始下一轮；② 「跳过问题」记成什么；③ 重试的语义；④ C 文档写的是单个 `pendingQuestion`，但 `决策记录.md` **B-3** 已定「一轮允许多个问题」，B7 实测一轮就是 3 个问题。
选项：
- **自动续轮**：**A 作答后自动开始下一轮（用户选择）**／B 作答后需再点一次发送。
- **跳过语义**：**A 记成一条真实回答（如「我暂时不想回答这个问题」）并进入下一轮（用户选择）**／B 仅关闭卡片、不下发任何内容。
- **重试语义**：**A 只允许重试最后一轮；重试期间保留原内容并显示「重新生成中」（用户选择）**／B 允许重试任意轮／C 重试时清空原内容。
- **待答状态**：**A 用数组 `pendingQuestions`（用户选择）**／B 保持单数 `pendingQuestion`（与 B-3 冲突）。
结论：
1. **作答即自动开始下一轮**，但实现方式必须是「命令内的原子转换」，不是 `useEffect` 观察条件（C 文档 2.4）。理由：effect 观察会在重复渲染时触发两次，且中间会出现「还没回答完就已经在生成」的混合态。
2. **跳过＝一条真实回答**：把「学生选择了跳过」写成 user 消息进入下一轮上下文（模板见 `01-核心协议.md` §6 的最后一行）。跳过按钮本身仍是可裁剪项（总纲 5.7），语义先定、界面后做。
3. **重试只针对最后一轮**：`retryLastTurn` 生成新 `runId` 重跑最后一条 turn，**保留原内容**直到新运行产出；运行中是空操作。界面入口（按钮放哪、怎么显示）留给 D/F，C 阶段只提供命令。
4. **待答状态用数组**：`state.pendingQuestions`（每项对应一次 `ask_question` 调用，字段与协议 §5 的 `questions[]` 一致）。C 文档与 `deriveViewState` 里的 `pendingQuestion` 一律按数组理解，**以本条为准**（C 文档正文保持原样，不擅自改写）。D4 的「问题卡组」因此按 `questions.length` 渲染。
原因：四条都指向同一件事——**界面不该靠猜**。自动续轮若不原子，双击或多一次渲染就会多发一轮；跳过若不落成文本，模型会读成「没有回应」并重复提问；重试若清空内容，用户会以为内容丢了；待答状态若仍是单数，一轮三问时界面只能显示一张卡，其余两个问题在状态里无处安放，D4 必然返工。B7 的真实运行（3 个问题各 5 档）已经把「一轮多问」从假设变成事实。
放弃的方案与理由：B（作答后再点发送）会改变既有交互风格，而本次改造明确不改变交互习惯，且演示时多一次点击；B（跳过只关卡片）会让下一轮上下文缺一条信息，模型可能又问同一个问题；B（重试任意轮）需要重建后续所有轮次，C 阶段时间不够且容易与「只重试最后一轮」的验收项冲突；C（重试清空）等于把可用内容当垃圾扔掉；B（单数 `pendingQuestion`）与 B-3 直接冲突，见上。
验证证据：用户 2026-10-17 对 1/2/3 逐条确认、第 4 条指定「改成数组」。本条为开工前置决策，**尚无运行证据**；C3 的用例（双击只产生一次运行、跳过进入上下文、重试保留原内容、一轮多问全部可查）落地后补齐。
遗留风险：（1）跳过按钮本期可能不做（可裁剪），届时「跳过」这条语义只有测试覆盖、没有界面入口；（2）「保留原内容 + 显示重新生成中」需要 D 阶段的双态渲染，C 阶段只保证 `parts` 不被清空；（3）`pendingQuestions` 与 `turns[].questions` 是两份视图，容易漂移——`pendingQuestions` 必须由 `deriveViewState` 从 turn 派生，不得独立存储。

## C 阶段 · 会话状态层

### C-3 阶段 C 结论：会话状态层

日期：2026-10-17

问题：旧路径的会话状态有两种投影各自可写（`messages` / `uiMessages`），作答摘要只进其一，已经出现内容分叉；运行状态靠可写布尔量，迟到的流会写回旧会话。C 阶段要把「谁在什么时候改状态」收回到一个地方，并让「答案如何进入下一轮上下文」有可验证的实现。

结论（7 条）：
1. **状态转换只有一个入口**：`src/utils/conversationState.js` 的 `reduceSession(state, action)`，14 个 action（7 个用户命令 + 7 个运行事件），纯函数：不依赖组件框架、不访问浏览器存储、不造随机 ID、不抛异常。
2. **运行事件的守卫是「`runId` 匹配 + 该 turn 仍 `streaming`」**，不匹配原样返回。第二半是必须的：取消/结束后同一 `runId` 的迟到片段如果只比 `runId` 就会被写进已收尾的轮次。
3. **待答状态是数组且不独立存储**：`pendingQuestions` 由 `deriveViewState` 从末轮 `questions` 派生，只在末轮 `awaiting_user` 时出现；`isRunning` 同样只有一处来源。
4. **`SUBMIT_ANSWER` / `SKIP_QUESTION` 一次 action 完成「写答案 → 问题改状态 →（该轮问题全部结束后）追加用户 turn → 起新运行」**，防双击靠 reducer 条件（问题须仍为 `pending`），不靠按钮 `disabled`。一轮多问时前几题只更新状态，最后一题才起新一轮（协议 §6：一轮的答案一起进上下文）。
5. **上下文显式组装**：`buildModelContext` 只纳入 `completed` / `awaiting_user` 的 turn，只保留配对成功的 `tool-call` / `tool-result`，丢弃 reasoning、空文本块、U+200B；用户答案用协议 §6 固定模板序列化，不用通用对象拼接。
6. **hook 只发命令、不返回 setter**：`useChatSession` 返回 20 个键（11 只读 + 9 命令）；每次运行一个 `AbortController`，随 `runId` 管理；`run-finished` 用运行层**返回值**派发（事件不带 `error`）。
7. **`parts` 元素带 `runId`**：重试换新 `runId` 时保留旧内容，新旧片段不互相拼接。

原因：这七条共同回答「界面不该靠猜」——状态不可双写、身份比布尔量可靠、答案必须有确定形态才能被断言。B7 的真实运行（一轮 3 问、结果乱序返回）已经把「一轮多问」和「结果顺序≠调用顺序」从假设变成事实。

- 分类逻辑抽成纯函数 `src/pages/AgentChatPage/errorAdapter.js` 的 `classifyTurnError(turn)`，返回 `{ kind, textKey, detail }`；顺序是 **timeout（看 `errorKind`）→ 工具不支持（看原文）→ 网络（看原文）→ 普通失败**。
- `TOOL_UNSUPPORTED_PATTERN` 从页面搬进该模块（行为不变，D-2 仍不自动降级）。
- `errorKind` 进存储白名单（只接受 `timeout` / `failed`，其余归 `null`），并计入保存签名，刷新后文案不丢。

原因：`endedBy` 在运行层本来就有，是**唯一可靠**的「超时 vs 其它失败」来源；只改 `error.message` 会把用户向文案写进运行层，且仍无法处理浏览器只有 `Failed to fetch` 一句的情况。

放弃的方案与理由：

- **只在展示层按字符串猜**：超时与取消在传输层同文案（「运行已中断」），必然误判，判据 4 做不出来。

- **加到 5 个新键（含工具不支持 / 副模型失败）**：这两条已有落点，重复加键会让同一状态有两个文案来源。
